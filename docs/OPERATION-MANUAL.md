# 業務オーケストレーション システム 操作マニュアル（MVP）

このマニュアルは、社内サーバーで動いている MVP について「何ができるか」と「どう操作するか」をまとめたものです。
読む人は、動作を確かめる QA の担当者と、これから運用を担当する職員を想定しています。

- 画面での操作を中心に書き、同じことを API で行う方法を各節の「API」に添えています。
- サーバーの立て方・更新・バックアップは [deploy/README.md](../deploy/README.md)、使い始めの作業は
  [deploy/GO-LIVE.md](../deploy/GO-LIVE.md) を見てください。
- API の正確な項目は `http://<サーバー>/api/openapi.json` で確認できます。

## 1. システムの概要

### 1.1 何をするシステムか

顧客ごとの定例業務について、「いつ行うか」（予定）と「実際にどう進んだか」（オーダー）を管理します。

- 業務ごとの予定をルールから自動で作り、カレンダーと日次ダッシュボードに出す
- 予定 1 件につき 1 件のオーダーを作り、リリース → 開始 → ステップの提出・承認 → 完了 まで記録する
- 手順書（SOP）を版で管理し、オーダーがどの版で作業するかをリリースの時点で固定する
- 締切が近いもの・過ぎたものを知らせ、月ごとの期限内率（SLA）を集計する
- 業務どうしの順番（依存関係）と、顧客側の出来事（ファイルの受領など）を扱う

### 1.2 用語

| 用語 | 意味 |
|---|---|
| 顧客 | 業務の依頼元。4 文字のコードで区別する |
| 業務 | 顧客ごとの仕事の単位。業務コード（顧客コード + 連番 4 桁）は自動で付く |
| SOP | 業務の手順書。版（草稿 → 予定 → 現行 → 過去）とステップを持つ |
| 予定テンプレート | 予定を作るルール（毎月 27 日、指定した日、年間計画シートの日付から何日前、など） |
| 予定 | テンプレートから作られた「この日時に行う」1 件 |
| オーダー | 予定 1 件に対する実作業の記録。状態と履歴を持つ |
| ステップ | オーダーの中の手順。SOP の版から、リリースの時点で作られる |
| 営業日カレンダー | 週末と休日の定義。休日に当たった予定の動かし方に使う |
| 信号 | 顧客側の出来事（例: ファイルが届いた）を外部の仕組みが知らせる通知 |

### 1.3 オーダーの状態

```
未リリース → リリース済 → 作業中 → 完了
                 ↘ 保留中（再開すると元の状態に戻る）
   どの状態からでも（完了を除く）→ 取消
```

| 状態 | 意味 |
|---|---|
| 未リリース | 予定はあるが、まだ作業に出していない。予定の変更に追従する |
| リリース済 | 作業に出した。SOP の版とステップがこの時点で固定される |
| 作業中 | 作業者が開始した。ステップを提出・承認できる |
| 保留中 | 一時的に止めている。再開すると止める前の状態に戻る |
| 完了 | すべてのステップが承認された（ステップのないオーダーは作業者が完了にする） |
| 取消 | 取り消した。履歴は残る |

オーダーには状態のほかに次の印が付きます。

| 印 | 意味 |
|---|---|
| 矛盾 | 予定が動いたのに、オーダーが追従できなかった（例: 作業中に休日が追加された）。解決するまでリリース・開始ができない |
| 待ち | 先に終わるべき上流のオーダーがまだ完了していない |
| まもなく | 締切が近い（テンプレートで決めた「何分前」から） |
| 遅れ | 締切を過ぎても完了・取消になっていない |

### 1.4 ロール

1 人が複数のロールを持てます。操作できるのは状態が「有効」の職員だけです。

| ロール | できること |
|---|---|
| 作業者 | オーダーの開始・保留・再開、ステップの提出、ステップのないオーダーの完了・受領、信号の対応 |
| 確認者 | ステップの承認・差し戻し（自分が提出したステップは不可） |
| リリース担当 | リリース、予定日前の開始の承認、依存関係を待たない開始の承認、SOP の版の指定、取消、矛盾の解決、カレンダーでの予定の変更、テンプレートの変更・シートの取り込みの内容の確認（保存・取り込みはできない） |
| 業務管理者 | 設定の変更すべて（顧客・業務・SOP・テンプレート・休日・依存関係）と、リリース担当と同じオーダーの操作（予定日前の開始の承認を除く） |
| 閲覧者 / 監査担当 | 参照のみ（監査担当は職員の一覧も見られる） |
| システム管理者 | 職員アカウントの管理（登録・ロール・有効化・仮パスワード・API キー）。業務の操作は含まない |
| 信号の送信 | 外部の仕組み用。API キーで信号を送るだけ |

### 1.5 画面の一覧

| 画面 | 場所 | 内容 |
|---|---|---|
| ログイン | `/login` | ログインID とパスワード |
| カレンダー | ナビ「カレンダー」 | 顧客ごとの月の予定。予定の変更・取消・臨時の予定 |
| 日次ダッシュボード | ナビ「日次ダッシュボード」 | 全顧客のその日の予定とオーダー。タブ: 予定 / 締切・遅れ / 信号 |
| SLA | ナビ「SLA」 | 顧客 × 月の期限内率。CSV の出力 |
| 設定 | ナビ「設定」のメニュー | 顧客 / 業務 / SOP / 予定テンプレート設定 / 年間計画シート / 休日カレンダー / 業務の依存関係 / 職員 |

右上の自分の名前のメニューに「パスワードを変更」と「ログアウト」があります。

### 1.6 自動で動く処理

| 処理 | いつ | 内容 |
|---|---|---|
| 自動リリース | 毎分 | リリースの方法が「自動」の業務で、決めた時刻を過ぎた未リリースのオーダーをリリース済にする |
| 予定の生成 | 毎日 00:05 | すべてのテンプレートの予定を約 90 日先まで作り足す。新しい予定にはオーダーも作る |
| バックアップ | 毎日 01:00 | データベースを `/srv/ops/backups/` に保存する（14 日分） |
| 画面の更新 | 2 分ごと | 日次ダッシュボードが開いている間、自動で読み直す |

## 2. 前提条件

### 2.1 画面を使うとき

- 社内ネットワークからブラウザで `http://<サーバーの IP アドレス>/` を開く（http。社外からは届きません）
- 職員アカウントがあり、状態が「有効」で、パスワードが設定されていること
- 操作に合ったロールを持っていること（1.4）

アカウントは システム管理者 が 設定 → 職員 で作ります（3.2）。最初の管理者だけはサーバーでコマンドから作ります
（[deploy/README.md](../deploy/README.md) の 1.）。

### 2.2 ログインのきまり

| 項目 | きまり |
|---|---|
| パスワード | 8〜128 文字。前後に空白を入れない。ログインID と同じものは不可 |
| 仮パスワード | システム管理者が設定したパスワード。最初のログインで本人が変えるまで、ほかの画面・API は使えない |
| ロック | 5 回続けて間違えると 15 分間ログインできない（システム管理者が仮パスワードを設定し直すと解除される） |
| ログインの期限 | 12 時間操作がないと切れる。操作していても最長 7 日 |
| ログインが切れるとき | ログアウト、利用停止、パスワードの変更・再設定（変更した本人の今の画面は残る） |

### 2.3 API を使うとき

API は画面と同じサーバーの `/api` の下にあります（例: `http://<サーバー>/api/ops/daily`）。
本文は JSON、文字コードは UTF-8、日時は ISO 8601（タイムゾーン付き）です。

認証は 2 通りです。

| 方法 | 使う場面 | やり方 |
|---|---|---|
| ログインの Cookie | 人の操作と同じことをする API すべて | `POST /api/auth/login` が返す Cookie `ops_session` を、以後の呼び出しに付ける |
| API キー | 信号の送信（`POST /api/ope/signals`）だけ | ヘッダー `Authorization: Bearer <キー>`。キーは システム管理者 が「信号の送信」ロールの職員に発行する（3.2） |

ログインなしで呼べるのは `POST /auth/login`、`POST /auth/logout`、`GET /openapi.json` だけです。
具体的な呼び方とエラーの形は 4. を見てください。

## 3. 機能ごとの手順

各節の「必要なロール」は、その操作をする人に必要なものです。見るだけなら、有効な職員であれば誰でも見られます
（職員の一覧だけは システム管理者・業務管理者・監査担当）。

### 3.1 ログイン・パスワードの変更・ログアウト

**ログイン**

1. `http://<サーバー>/` を開く。ログインしていなければログイン画面になる
2. ログインID とパスワードを入れてログインする
3. 仮パスワードのときは「パスワードを変更してください」の画面になる。今のパスワードと新しいパスワード（2 回）を入れる

**パスワードの変更**: 右上の名前 →「パスワードを変更」。

**ログアウト**: 右上の名前 →「ログアウト」。

主なエラー: 「ログインIDまたはパスワードが違います。」/ ロック中（解除される時刻が出る）/ アカウントが利用開始前・停止中。

**API**

| 操作 | 呼び出し |
|---|---|
| ログイン | `POST /auth/login` `{"login_id": "...", "password": "..."}` → 職員の情報 + Cookie |
| 自分の情報 | `GET /staff/me` |
| パスワードの変更 | `POST /auth/password` `{"current_password": "...", "new_password": "..."}` |
| ログアウト | `POST /auth/logout` |

### 3.2 職員の管理

必要なロール: システム管理者。画面: 設定 → 職員。

**職員を登録する**

1. 「職員を登録」を押し、ログインID・氏名・メールアドレス（任意）・ロールを入れる
2. 登録した直後の状態は「利用開始前」。行の「有効化」を押す
3. 行の「仮パスワード」を押してパスワードを決め、本人に伝える（一覧に「仮パスワード」の印が付く）
4. 本人が最初のログインで自分のパスワードに変える

**そのほかの操作**

| したいこと | 操作 |
|---|---|
| 氏名・メール・ロールを変える | 行の「編集」（自分のシステム管理者ロールは外せない） |
| 使えなくする / 戻す | 「利用停止」/「再開」（自分の行は不可。停止するとログインも切れる。ロールは残る） |
| パスワードを忘れた・ロックされた | 「仮パスワード」で設定し直す（自分自身には不可。自分の分は右上のメニューから） |
| 信号の送信用のキーを発行する | 「信号の送信」ロールの職員の行で「API キー」→ ラベルを入れて「発行」。**キーの全文はこのときだけ表示される**ので控える。不要になったら「取り消す」 |

職員は削除できません（履歴に名前が残るため）。使わなくなったら利用停止にします。
一覧の印: パスワード未設定 / 仮パスワード / ロック中。

**API**

| 操作 | 呼び出し |
|---|---|
| 一覧 / 1 件 | `GET /staff/`、`GET /staff/{id}` |
| ロールの一覧 | `GET /staff/roles` |
| 登録 | `POST /staff/` `{"login_id", "name", "email", "roles": ["operator", ...]}` |
| 氏名・メール | `PATCH /staff/{id}` |
| ロール | `PUT /staff/{id}/roles` `{"roles": [...]}` |
| 状態 | `PUT /staff/{id}/status` `{"status": "active"}`（または `"suspended"`） |
| 仮パスワード | `PUT /staff/{id}/password` `{"password": "..."}` |
| API キー | `GET /staff/{id}/api-keys`、`POST /staff/{id}/api-keys` `{"label": "..."}`、`POST /staff/api-keys/{key_id}/revoke` |

ロールのコード: `operator` 作業者 / `checker` 確認者 / `releaser` リリース担当 / `admin` 業務管理者 / `viewer` 閲覧者 /
`auditor` 監査担当 / `system_admin` システム管理者 / `signal_sender` 信号の送信。

### 3.3 顧客

必要なロール: 業務管理者。画面: 設定 → 顧客。

1. 「顧客を登録」を押し、顧客コード（英数字 4 文字。大文字になる。**あとで変えられない**）と顧客名を入れる
2. 名前を直すときは行の「名前を変更」
3. 取引が終わった顧客は「無効にする」。一覧や選択肢に出なくなり、業務・シートを新しく作れなくなる（履歴は残る）。戻すときは「有効にする」

顧客は削除できません。有効な業務が残っている顧客は無効にできません（先に業務を削除する）。

**API**: `GET /clients/?include_inactive=true`、`POST /clients/` `{"code", "name"}`、`PATCH /clients/{id}` `{"name"}`、
`POST /clients/{id}/deactivate`、`POST /clients/{id}/activate`。

### 3.4 業務と業務の設定

必要なロール: 業務管理者。画面: 設定 → 業務（顧客を選ぶ）。

**業務を登録する**

1. 顧客を選び、「業務を登録」を押す。業務コードは自動で決まり、画面に表示される（登録後は変えられない）
2. 業務名、管理者のメールアドレス（任意）、説明（任意）を入れる

**業務の設定を決める**: 業務の行の「予定テンプレート・業務の設定」→ 業務の設定の「編集」。

| 項目 | 選択肢 | 意味 |
|---|---|---|
| リリースの方法 | 手動（リリース担当が承認）/ 自動（指定の時刻に） | 自動にすると、決めた時刻にシステムがリリースする |
| 自動リリース: 予定日の何日前 | 0〜30（0 = 当日） | |
| 自動リリースの時刻 | 既定 03:00（日本時間） | |
| 実行のしかた | SOP のステップで作業する / 顧客側の出来事（ステップなし） | 後者はファイルの受領など、ステップのない業務 |
| 完了のしかた | 作業者が受領を記録する / 信号で自動的に完了する | 「信号で自動」は「顧客側の出来事」のときだけ選べる |
| 信号の種類 | 文字列 | 「信号で自動」のとき必須。送信側と同じ値にする。同じ顧客の中で重複不可 |

**削除と復元**: 行の「削除」/「元に戻す」。次のどれかがあると削除できません（理由が表示されます）:
依存関係の定義、有効な予定テンプレート、完了・取消になっていないオーダー。

**API**

| 操作 | 呼び出し |
|---|---|
| 一覧 | `GET /biz/?client_code=XXXX&include_deleted=true` |
| 登録 | `POST /biz/` `{"client_code", "name", "manager_email", "description"}` |
| 編集・業務の設定 | `PATCH /biz/{id}`（`release_mode`、`release_time`、`release_days_before`、`execution_type`、`completion_mode`、`signal_type` など、変える項目だけ） |
| 削除 / 復元 | `DELETE /biz/{id}`、`POST /biz/{id}/restore` |

### 3.5 SOP（手順書の版とステップ）

必要なロール: 業務管理者。画面: 設定 → SOP（業務を選ぶ）。左に版の一覧、右に選んだ版のステップ。

版の状態:

| 状態 | 意味 | 編集 |
|---|---|---|
| 草稿 | 作成中 | できる |
| 予定 | 承認済みで、使い始めの日がまだ来ていない | できない（承認を取り消せば草稿に戻る） |
| 現行 | 今使われている | できない |
| 過去 | 次の版に替わった | できない |

**新しい版を作って使い始める**

1. 「新しい版」を押し、タグ（例: `v1.1.0`）を決める。最新の承認済みの版があればその内容が写される（最初は空）
2. 「ステップを追加」で手順を入れる
   - 手順（題名）、内容
   - 含める条件: 毎回 / 指定した月だけ / 週の最初の予定だけ
   - 「承認で次へ」: チェックすると、このステップが**承認**されるまで次のステップが開かない（付けなければ**提出**で次が開く）
3. 並べ替えは ↑ / ↓、直すときは「編集」、消すときは「削除」。番号が飛んだら「番号を振り直す」
4. 「承認…」を押し、使い始めの日を選ぶ（**最も早くて明日**。その日の 00:00 日本時間から有効）
   - 画面に、影響を受けるオーダーが 3 つに分けて出る: 新しい版を使うオーダー / 指定した版のまま / リリース済み（固定した版のまま）
5. 承認すると版は「予定」になり、使い始めの日に「現行」になる。それまでの現行の版は前日までになる

きまり:

- ステップが 1 つもない草稿は承認できない
- 「予定」の版は同時に 1 つだけ。別の版を承認するには、先の「予定を取り消す」か、使い始めの日を待つ
- 「予定を取り消す」は使い始めの日の前だけ。その版を指定・固定しているオーダーがあると取り消せない
- **リリース済みのオーダーは、あとから版が替わっても変わらない**（リリースの時点の版とステップのまま）
- 使い始めの日より前の予定のオーダーは、その日に有効な版で作業する。有効な版がない日のオーダーはステップなしでリリースされる

**API**

| 操作 | 呼び出し |
|---|---|
| 版の一覧 | `GET /biz/{biz_id}/versions?include_drafts=true` |
| 版とステップ | `GET /biz/versions/{version_id}` |
| 新しい版（写して作る） | `POST /biz/{biz_id}/versions/clone` `{"version_tag": "v1.1.0"}` |
| タグを変更 / 草稿を削除 | `PATCH /biz/versions/{id}`、`DELETE /biz/versions/{id}` |
| ステップの追加 | `POST /biz/versions/{id}/steps` `{"title", "content", "condition": {"type": "always"}, "is_blocking": false}` |
| ステップの編集 / 削除 | `PATCH /biz/steps/{step_id}`、`DELETE /biz/steps/{step_id}` |
| 並べ替え | `PUT /biz/versions/{id}/steps/order` `{"step_ids": [3, 1, 2]}` |
| 影響の確認 | `GET /ope/sop-impact?biz_id=1&effective_date=2026-11-20` |
| 承認 | `POST /biz/{biz_id}/versions/{draft_id}/approve` `{"effective_date": "2026-11-20"}` |
| 予定を取り消す | `POST /biz/{biz_id}/versions/{version_id}/cancel` |

条件の書き方: `{"type": "always"}` / `{"type": "month_in", "months": [3, 9]}` / `{"type": "first_in_week"}`。

### 3.6 休日カレンダー

必要なロール: 業務管理者。画面: 設定 → 休日カレンダー（カレンダーと年を選ぶ）。

1. 「日本の祝日を取り込む」で、その年の祝日（振替休日・国民の休日を含む）をまとめて登録する
2. 会社や銀行の休業日（例: 12/31、1/2、1/3）は「休日を追加」で足す
3. 名前の変更・削除は行の操作から

きまり:

- **今日より前の休日は変えられない**（実績と食い違うため）
- 休日を足す・消すと、そのカレンダーを使うテンプレートの**今日以降の予定が作り直される**（人が変更した予定はそのまま）。
  オーダーも追従する（追従できないものには「矛盾」が付く）
- 祝日は法律の規定から計算している。内閣府の発表と違うときは取り込んだあとで直す

カレンダーそのものを作る画面はありません。最初のカレンダー（`JP_BANK` 銀行営業日、土日休み）はサーバーで
`scripts/setup_calendar.py` を 1 回動かして作ります（[deploy/GO-LIVE.md](../deploy/GO-LIVE.md) の B）。

**API**: `GET /plans/calendars`、`GET /plans/calendars/{id}/holidays`、
`POST /plans/calendars/{id}/holidays` `{"holidays": [{"holiday_date": "2026-12-31", "name": "年末休業"}]}`、
`DELETE /plans/calendars/{id}/holidays/2026-12-31`。

### 3.7 予定テンプレート

必要なロール: 業務管理者（作成・変更・削除）。リリース担当は、内容の確認までできる（下の「リリース担当ができること」）。
画面: 設定 → 予定テンプレート設定（業務を選ぶ）。

**テンプレートを作る**: 「新規作成」を押して次を決める。

| 項目 | 内容 |
|---|---|
| 種類 | 繰り返しルール / 顧客指定日 / 年間計画シート |
| 予定名、分類、表示色・アイコン | カレンダーでの見え方 |
| 開始時刻、所要時間（分）、タイムゾーン | 予定の時間帯 |
| 起点日、繰り返しルール（RRULE） | 種類が繰り返しルールのとき。例: `FREQ=MONTHLY;BYMONTHDAY=27`、`FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR` |
| 指定日 | 種類が顧客指定日のとき。日付を並べる |
| 年間計画シート、参照するマーカー、基準日のずれ、日数の数え方、時刻のずれ | 種類が年間計画シートのとき。シートの日付から「3 営業日前」などを決める |
| 営業日カレンダー、非営業日に当たった場合 | 休日も実施 / 休日はスキップ / 翌営業日 / 前営業日 / 翌営業日（月をまたぐ場合は前営業日）/ 前営業日（月をまたぐ場合は翌営業日） |
| 締切の決め方 | 予定の終了（開始時刻 + 所要時間）/ 開始から（何分後）/ 固定の時刻（予定日の何日後の何時） |
| 締切の何分前に「まもなく」を出すか | 0 = 出さない |

作ると、すぐに先の予定（約 90 日先まで、少なくとも次の 1 件）ができ、**予定ごとに未リリースのオーダーができます**。
作る前に「予定を確認」を押すと、その内容でできる予定を月ごとの小さなカレンダーで見られます（任意。何も保存されません）。

**変更したとき**

- 時刻・ルール・休日の扱いなどを変えると、**未来の予定だけ**が作り直される。過去の予定と、人が変更・取消した予定はそのまま
- **オーダーが完了・作業中の予定も、そのまま残る**（終わった作業・始まった作業の予定は動かさない。オーダーとつながったまま、今の日時で表示される）。
  今日の予定で、元の時刻がもう過ぎているものも動かない
- その場合は、「保存する」を押すと先に **「保存の前の確認」** が開く（下の「保存の前の確認」）。名前・締切・表示だけの変更は、そのまま保存される
- 締切の項目を変えると、**未リリースのオーダーだけ**に反映される（リリース済み以降は変わらない）
- 削除すると未来の予定は消え、未リリース・リリース済のオーダーは取消になる。過去は残る

一覧の「次の予定」が空で警告の印が付いているテンプレートは、この先 2 年に予定がありません（ルールや指定日を見直す）。

**保存の前の確認**

テンプレートを変えると、予定とオーダーがすぐに動きます。保存する前に、何が起きるかを確かめるための画面です。
システムが実際の保存を試しに行い、結果を読み取ってから取り消すので、**表示される内容は、保存したときに起きることと同じ**です
（この画面を開いただけでは、何も保存されません）。

1. テンプレートの「編集」で項目を変えて「保存する」。日付に関わる変更なら、確認の画面が開く
2. 上の要約を読む:

   | 表示 | 意味 |
   |---|---|
   | 増える / 無くなる / 日時が変わる | 予定の違い。曜日や日にちのルールを変えたときは、元の日が「無くなる」、新しい日が「増える」になる |
   | 人が変更・追加した予定 N 件は、そのまま残ります | 1 日だけ動かした・取り消した予定は、テンプレートを変えても変わらない |
   | オーダー N 件の日時が変わります（うちリリース済み・保留中 n 件） | 予定に追従するオーダー。リリース済みのものは、現場がもう見ている |
   | オーダー N 件が取消になります | 予定が無くなるオーダー（未リリース・リリース済） |
   | オーダー N 件が「矛盾」になります | 保留中のオーダーの予定が無くなるときなど、自動では決めないもの。保存の後、日次ダッシュボードで人が判断する（3.11） |
   | オーダーが新しく N 件できます | 増える予定の分 |

3. 月ごとのカレンダーで日を確かめる。色の意味は上の凡例のとおり（無くなる日は取り消し線、人が変更した日は破線の枠）。日にマウスを置くと時刻が出る
4. 範囲は 3 か月（既定）/ 6 か月 / 12 か月を選べる。もう作られている予定の範囲のほうが長いときは、そこまで表示される
5. 下の一覧を開くと、日付と、影響するオーダー（今の状態・今の予定・保存するとどうなるか）を 1 件ずつ見られる
6. よければ「この内容で保存する」。直すときは「戻って直す」

知っておくこと:

- **動かない予定**: オーダーが完了・作業中の予定と、今日の予定で元の時刻がもう過ぎているものは、変更の対象にならない
  （確認の件数にも入らない）
- 顧客指定日のテンプレートの、指定日の追加・削除は確認に含まれない（画面にその旨が出る）
- この業務を待っている別の業務のオーダー（依存関係）は、影響するオーダーの一覧には出ない
- 確認を取れなかったとき（エラー）は、保存されない

**リリース担当ができること（確認だけ）**

リリース担当は準備に加わり、保存は業務管理者が行います（下書きを保存して承認に回す仕組みは、まだありません）。

1. テンプレートの行の「変更を確認」（新しいテンプレートは「新しいテンプレートの予定を確認」）を押す。業務管理者と同じフォームが開く
2. 項目を入れて「変更を確認」（または「予定を確認」）を押すと、上と同じ確認の画面が出る。予定の違いとオーダーへの影響を見られる
3. 保存・作成のボタンは出ない。**入力した内容は保存されない**ので、よければその内容を業務管理者に伝え、業務管理者が同じ内容を入れて保存する

**API**: `GET /plans/templates?biz_id=1`、`POST /plans/templates`、`PATCH /plans/templates/{id}`、`DELETE /plans/templates/{id}`、
指定日の追加・削除 `POST /plans/templates/{id}/dates` `{"dates": ["2026-12-01"]}`、`DELETE /plans/templates/{id}/dates/2026-12-01`。
作成の本文は種類ごとに項目が違うため、`/api/openapi.json` の `POST /plans/templates` を見てください。

保存の前の確認（リリース担当・業務管理者。何も保存しない。`months` は 1〜12、既定 3）:

- 変更: `POST /ops/templates/{id}/preview?months=3`、本文は `PATCH /plans/templates/{id}` と同じ（例: `{"start_time": "14:00:00"}`）。
  返るもの: `generation_changed`（false なら日付は変わらない）、`occurrences`（変更の後の予定）、`added` / `removed` / `moved`、
  `manual_unchanged`、`orders_total`、`orders_created`、`order_effects`（`rescheduled` / `canceled` / `conflict` と、今の状態）
- 新規: `POST /ops/templates/preview?months=3`、本文は `POST /plans/templates` と同じ。返るもの: `occurrences`、`orders_created`
- 入力の誤りは、実際の変更・作成と同じエラーになる

### 3.8 年間計画シート

顧客の年間計画（例: 振込日、締め日）の日付を持ち、テンプレートがそこから「何日前」と計算するためのものです。
1 つのシートに、日付の種類（マーカー）がいくつも入ります。必要なロール: 見るのは誰でも、変更・取り込みは業務管理者。リリース担当は、取り込みの内容の確認までできる。画面: 設定 → 年間計画シート（顧客を選ぶ）。

**役割の分担:** 顧客から届く表（Excel など）をシステムは読みません。表から決まった形の JSON ファイルへの変換は、**利用者の側**（システムの外）で行い、
システムはその JSON ファイルだけを受け取ります。

#### シートを取り込む（新しく作る・日付を足す）

1. 設定 → 年間計画シート → 顧客を選ぶ →「シートを取り込む」
2. JSON ファイルを置くか、クリックして選ぶ。読めないファイル・項目の足りないファイルは、理由がすべて表示されて止まる
3. 表示を確かめる: 顧客コード、シート名（「新しく作る」か「既にあるシートを更新」か）、期間、マーカーと日付の件数、「取り込むと: …」の件数
4. 既にあるシートの場合は、取り込み方を選ぶ:

   | 取り込み方 | 動き | 使う場面 |
   |---|---|---|
   | 追加だけ（既定） | ファイルにある日付で、まだ無いものを追加する。今ある日付は消さない。シートの期間は、今のシートとファイルの両方を含むように広がる | **次の年の分が届いたとき**（その年だけのファイルでよい）、日付の追加 |
   | ファイルに合わせる | 追加に加えて、ファイルに無い日付を削除し、期間もファイルのとおりにする | 顧客が表を出し直し、無くなった日付を消したいとき |

5. 「取り込む」。結果（追加したマーカー・説明を変えたマーカー・追加した日付・削除した日付・予定を作り直したテンプレート）が表示される

**リリース担当ができること（確認だけ）**: 「取り込みの内容を確認」を押すと同じ画面が開き、ファイルを選んで、上の 2〜4（内容の表示・
取り込み方ごとの「取り込むと: …」の件数・警告）までを見られる。取り込みのボタンは出ない。ここまではブラウザの中の計算で、ファイルは
サーバーに送られない。よければ、そのファイルと取り込み方を業務管理者に伝え、業務管理者が取り込む。

決まり:

- 同じシートかどうかは **顧客コード + シート名** で決まる。同じなら更新、無ければ新しく作る。毎年同じシート名を使う（テンプレートは 1 つのシートのマーカーを参照するため、年ごとに別のシートにしない）
- 同じファイルをもう一度取り込んでも、何も変わらない
- 全体が 1 つのまとまりで、エラーのときは何も反映されない
- **人が変更・追加・取消した日付は、どちらの取り込み方でも変わらない**（人が取り消した日付は、ファイルにあっても戻らない）
- 「ファイルに合わせる」では、**ファイルに日付が 1 件も無いマーカーは日付がすべて消える**（取り込む前に、マーカー名と件数が警告に出る）。全マーカーの全期間の日付を入れたファイルで行う
- ファイルに無いマーカーそのものは消えない（テンプレートが参照しているかもしれないため）
- ルールで日付を作るマーカーの日付は、取り込めない（ファイルに入っていると止まる）。ファイルから外すか、画面で 1 件ずつ変える
- ファイルの顧客コードが、選んでいる顧客と違うときは止まる
- 日付が変わったマーカーを参照するテンプレートは、未来の予定が作り直される
- 取り込みでは今日より前の日付も入れられる（最初の取り込みのため）

#### JSON ファイルの形

```json
{
  "client_code": "ABCD",
  "sheet_name": "年間計画",
  "period_start": "2026-04-01",
  "period_end": "2027-03-31",
  "markers": [
    {"marker": "本締", "description": "月次の本締め"},
    {"marker": "送付", "description": null}
  ],
  "events": [
    {"event_date": "2026-04-24", "marker": "本締"},
    {"event_date": "2026-04-27", "marker": "送付"}
  ]
}
```

| 項目 | 決まり |
|---|---|
| `client_code` | 登録済みで有効な顧客のコード（4 文字） |
| `sheet_name` | 1〜100 文字 |
| `period_start` / `period_end` | `YYYY-MM-DD`。終わりは始まりより後 |
| `markers` | 1〜100 件。`marker` は 1〜50 文字で、ファイルの中で重複しない。`description` は 200 文字まで（無くてもよい） |
| `events` | 0〜20,000 件。`event_date` は期間の中の日付、`marker` は `markers` にある名前 |

- 「動かさない日」（元の表の × など）は書きません。**ある日付だけ**を書きます。日付を消すのは「ファイルに合わせる」で、ファイルに無いことによって行います
- 文字コードは UTF-8。画面から取り込めるのは 4MB まで（20,000 件の日付で 1MB ほど）
- 見本: リポジトリの `mock_data/desensitized_mock_data.json`

#### API で取り込む場合

`POST /plans/sheets/import`（業務管理者でログインした Cookie が要る。本文は上の JSON そのまま）。新しく作ったときは 201、更新したときは 200。
「ファイルに合わせる」は `POST /plans/sheets/import?replace_events=true`。

**画面との違い:** API は期間を広げません。シートの期間はファイルの期間に置き換わり、「追加だけ」（`replace_events` なし）で今ある日付が新しい期間の外に出ると
400 で止まります。次の年の分を API で足すときは、`period_start` を今のシートの始まりのままにし、`period_end` だけを延ばしてください。

#### マーカーと日付を画面で直す

- 「ルールで日付を作るマーカーを追加」: 毎月 27 日のように決まりで作れる基準日を、シートの期間全体に作る（休日の扱いと営業日カレンダーを選べる）。「編集」でルールを変える、「生成をやめる」で止める
- マーカーの行を開くと日付の一覧: 日付の追加・変更・削除・ルールに戻す。出どころ（ルール / 人が変更 / 人が追加 / 取消 / 取り込み）が表示される
- 今日より前の日付は変えられません。日付を変えると、それを参照するテンプレートの未来の予定が作り直されます
- 空のシートだけを作る画面はありません（API `POST /plans/sheets` はある）。マーカーだけで日付の無いファイルを取り込めば、同じことができます

### 3.9 業務の依存関係

必要なロール: 業務管理者。画面: 設定 → 業務の依存関係（顧客を選ぶ）。同じ顧客の業務どうしだけ設定できます。

1. 「依存関係を追加」を押す
2. 上流（先に終わる業務）と下流（上流の完了を待つ業務）を選ぶ
3. 突き合わせ（下流のオーダーがどの上流のオーダーを待つか）を選ぶ

   | 突き合わせ | 待つ相手 |
   |---|---|
   | 同じシート日付 | 年間計画シートの同じ日付から作られた予定どうし |
   | 同じ日付 | ルール上の同じ日付の予定どうし（休日で動いても元の日付で突き合わせる） |
   | 直前の上流 | 下流の開始より前で最も近い上流のオーダー。何日前まで探すかを決める（既定 35 日） |

4. 種類を選ぶ: 「待つ」（上流が完了するまで下流を開始できない）/「参考」（表示するだけ）

変更はできません（削除して作り直す）。循環する設定（A → B → A）は保存できません。

待っている下流のオーダーには日次ダッシュボードで「待ち」が付き、「開始」が出ません。上流を待たずに始めるときは
リリース担当か業務管理者が理由を入れて承認します（3.11）。上流が取消・保留になっても、下流は自動では開始できるようになりません。

**API**: `GET /biz/clients/{client_code}/dependencies`、
`POST /biz/{下流の biz_id}/dependencies` `{"upstream_biz_id": 1, "match_rule": "same_occurrence_date", "kind": "hard"}`
（`match_rule`: `same_sheet_event` / `same_occurrence_date` / `latest_before`（`lookback_days` が必須）、`kind`: `hard` / `informational`）、
`DELETE /biz/dependencies/{id}`。

### 3.10 カレンダー（予定を見る・動かす）

画面: ナビ「カレンダー」。顧客と月を選ぶと、その月の予定が日ごとに並びます。分類や予定名で表示を絞れます。
日をダブルクリックすると、その日の日次ダッシュボードが開きます。

予定を動かす操作に必要なロール: リリース担当 または 業務管理者（ほかの職員は見るだけ）。

| 操作 | やり方 | 結果 |
|---|---|---|
| 日時を変える | 予定の「変更」→ 新しい日時を入れて「変更する」 | 予定が動き、オーダーも追従する |
| 取り消す | 予定の「取消」→「取り消す」 | 予定が消え、オーダーは取消になる |
| ルールどおりに戻す | 変更した予定の「元に戻す」 | ルールの日時に戻る |
| 臨時の予定を足す | 「臨時の予定」→ テンプレートと日時を選んで「追加する」 | その 1 回だけの予定とオーダーができる |
| 取り消した予定を戻す | 「取消済みの予定」の一覧 →「元に戻す」 | 予定が戻り、新しいオーダーができる（取消になったオーダーは履歴として残る） |

きまり:

- **作業中のオーダーの予定は、人が変更・取消できない**（エラーになる）。オーダー側で保留・取消をする
- 人が変更・取消した予定は、ルールや休日を変えても自動では作り直されない
- リリース済のオーダーの予定を動かして、ステップの条件（月・週の最初）の当てはまり方が変わると「矛盾」が付く

**API**: `GET /plans/clients/{code}/calendar?month=2026-11`、
`POST /plans/instances/{id}/override` `{"scheduled_start": "2026-11-20T09:00:00+09:00", "note": "..."}`、
`POST /plans/instances/{id}/cancel`、`POST /plans/instances/{id}/revert`、
`POST /plans/templates/{id}/instances` `{"scheduled_start": "..."}`（臨時）、
`GET /plans/clients/{code}/cancelled?start=...&end=...`、`POST /plans/instances/{id}/restore`。

### 3.11 日次ダッシュボードとオーダーの操作

画面: ナビ「日次ダッシュボード」。日付を選ぶと、全顧客のその日に始まる予定が 顧客 → 業務 の順に並びます。

- 行に出るもの: 時刻、予定名、オーダーの状態、ステップの進み（例 `2/3`）、矛盾 / 待ち / まもなく / 遅れ、締切（予定の終了と違うとき）
- 行を押すと右にオーダーの詳細が開く: 状態、予定、SOP の版、締切、ステップ、依存関係、記録（誰がいつ何をしたか）
- 歯車の印から、その予定のテンプレートの設定へ移れる
- 過去の日付では、取り消された予定も理由付きで表示される

**オーダーの操作**（詳細の中のボタン。自分のロールと状態で使えるものだけ出ます）

| 操作 | 必要なロール | できる状態 | 条件・理由の入力 | API（`POST /ope/orders/{id}/…`） |
|---|---|---|---|---|
| リリース | リリース担当・業務管理者 | 未リリース | 矛盾がないこと。自動の業務でも手で出せる | `release` |
| 開始 | 作業者 | リリース済 | 予定日（日本時間）以降。矛盾がないこと。待つ上流が完了していること | `start` |
| 予定日前の開始を承認 | リリース担当 | 未リリース・リリース済 | 予定日より前に始めたいとき。承認後に作業者が開始する | `approve-early-start` |
| 依存関係を待たずに開始を承認 | リリース担当・業務管理者 | 未リリース・リリース済 | **理由が必須**。承認後に作業者が開始する（予定日のきまりは別に残る） | `approve-dependency-override` |
| 保留 | 作業者・リリース担当・業務管理者 | 未リリース・リリース済・作業中 | **理由が必須**。保留中はステップを操作できない | `hold` |
| 再開 | 同上 | 保留中 | 止める前の状態に戻る | `resume` |
| 完了 / 受領 | 作業者 | 作業中（顧客側の出来事はリリース済からも） | **ステップのないオーダーだけ**。「信号で自動」の業務を手で完了にするときは理由が必須 | `finish` |
| 取消 | リリース担当・業務管理者 | 完了・取消以外 | **理由が必須**。カレンダーの予定も取り消される | `cancel` |
| 矛盾を解決 | リリース担当・業務管理者 | 矛盾が付いているとき | 下の 3 つから選ぶ | `resolve-conflict` |
| SOP バージョンを指定 / 解除 | リリース担当・業務管理者 | 未リリース | その業務の承認済みの版から選ぶ | `pin`、`unpin` |

矛盾の解決の選択肢:

| 選択肢 | 結果 |
|---|---|
| 予定の新しい日時を採用 | オーダーを今の予定に合わせる。予定がなくなっていれば取消。開始前でステップの当てはまりが変わっていれば、ステップを作り直す |
| このまま続ける | 印だけ消す。ステップは今のまま |
| オーダーを取り消す | 理由が必須 |

ステップのあるオーダーは「完了」のボタンが出ません。最後のステップが承認されると自動で完了になります。
矛盾が付いている間は、最後のステップが承認されても作業中のままで、矛盾を解決すると完了になります。

**API**: 一覧 `GET /ops/daily?date=2026-11-10`、詳細 `GET /ope/orders/{id}`。
操作の本文は、理由が必須のもの `{"reason": "..."}`、任意のメモ `{"comment": "..."}`、
矛盾の解決 `{"action": "accept_plan"}`（`accept_plan` / `keep` / `cancel`）、版の指定 `{"sop_version_id": 3, "reason": "..."}`。

### 3.12 ステップの提出・承認・差し戻し

場所: オーダーの詳細の「ステップ」。オーダーが**作業中**のときだけ操作できます。

ステップの状態: 待機（まだ開いていない）→ 未提出 → 確認待ち → 承認済。

1. 作業者がオーダーを「開始」すると、最初のステップが「未提出」になる
2. 作業者が作業を終えて「提出」を押す（メモは任意）→「確認待ち」
3. 確認者が内容を確かめて「承認」を押す →「承認済」。直しが要るときは「差し戻し」（**理由が必須**）→ そのステップだけ「未提出」に戻る
4. 次のステップは、前のステップの**提出**で開く。前のステップに「承認で次へ」が付いていれば**承認**で開く
5. すべてのステップが承認されると、オーダーは自動で「完了」になる

きまり:

- **自分が提出したステップは、自分では承認・差し戻しできない**（作業者と確認者の両方のロールを持っていても）。別の人が提出し直せば、最初の提出者は承認できる
- 差し戻しても、先のステップの状態は変わらない
- リリースの前は、ステップは「予定」として表示されるだけ（条件に当てはまるものの見込み）

**API**: `POST /ope/steps/{step_id}/submit`、`POST /ope/steps/{step_id}/approve`、
`POST /ope/steps/{step_id}/reject` `{"reason": "..."}`。ステップの番号（`step_id`）は `GET /ope/orders/{id}` の `steps` にあります。

### 3.13 締切・遅れの確認

場所: 日次ダッシュボードのタブ「締切・遅れ」。タブに件数が出ます（遅れがあれば赤、まもなくだけなら金色）。

- 日付に関係なく、完了・取消になっていないオーダーのうち「まもなく」と「遅れ」のものが、締切の早い順に並ぶ
- 行を押すとオーダーの詳細が開く
- 締切はテンプレートで決めたきまり（3.7）から、オーダーに記録される。リリースの後にテンプレートを変えても変わらない。
  予定が動いたときは、オーダーが持っているきまりで計算し直される

**API**: `GET /ops/attention?limit=100`。

### 3.14 顧客側の出来事と信号

ファイルの受領のような「顧客側で起きること」を、ステップのない業務として扱います（3.4 で 実行のしかた = 顧客側の出来事）。

**手で受領を記録する（完了のしかた = 作業者が受領を記録する）**

1. オーダーがリリース済になったら、作業者が顧客からの受領を確かめる
2. オーダーの詳細で「受領」を押す → 完了。開始の操作は要らない

**信号で自動的に完了する（完了のしかた = 信号で自動的に完了する）**

外部の仕組みが `POST /api/ope/signals` を呼ぶと、当てはまるオーダーが自動で完了になります。

- 照合: 信号の種類（業務の設定と同じ値）+ 顧客コード + キー（オーダーのルール上の日付 `YYYY-MM-DD`）
- 完了にできるのは、リリース済か作業中のオーダーだけ

| 結果 | 意味 |
|---|---|
| 完了にした | 当てはまるオーダーが 1 件あり、完了にした |
| 重複（すでに完了） | そのオーダーはもう完了している（同じ信号がもう一度来た） |
| 照合できない | 当てはまるオーダーがない、まだ未リリース、保留中、矛盾がある、キーが日付でない、など |
| 候補が複数 | 当てはまるオーダーが 2 件以上ある |

信号はどの結果でも記録に残ります。「照合できない」と「候補が複数」は人の対応が必要です。

**対応する**（作業者・リリース担当・業務管理者）: 日次ダッシュボードのタブ「信号」→ 行の「対応」→
メモ（必須）と、完了にするオーダーの番号（任意）を入れる。対応は 1 回だけで、あとから変えられません。

信号が来ないとき: 作業者がオーダーの詳細で「受領」を押し、理由を入れて完了にできます。

**API**

| 操作 | 呼び出し |
|---|---|
| 信号を送る | `POST /ope/signals`（**API キー**）`{"type": "data_received", "client_code": "ABCD", "key": "2026-11-10", "received_at": "2026-11-10T08:55:00+09:00"}` |
| 一覧 | `GET /ope/signals?scope=open`（`open` = 対応待ち / `all`） |
| 対応 | `POST /ope/signals/{id}/handle` `{"note": "...", "order_id": 123}` |

### 3.15 SLA レポート

画面: ナビ「SLA」。有効な職員なら誰でも見られます。

1. 月の範囲（既定は直近 12 か月、最長 36 か月）と顧客を選ぶ
2. 顧客 × 月（**締切のある月**、日本時間）ごとに次が出る

   | 列 | 意味 |
   |---|---|
   | 完了 | その月が締切で、完了したオーダーの数 |
   | 遅れ | そのうち、締切より後に完了した数 |
   | 期限内率 | （完了 − 遅れ）÷ 完了 |
   | 平均遅れ（分） | 遅れたオーダーだけの平均 |
   | 未完了の遅れ | 締切を過ぎてまだ完了していない数（上の数字には入らない） |

3. 「CSV を出力」で、表示している行をそのまま保存する（Excel で開ける）

取消になったオーダーは数えません。

**API**: `GET /ops/sla?from=2026-01&to=2026-11&client_code=ABCD`。

## 4. API の呼び方

### 4.1 ログインして呼ぶ（curl の例）

```sh
BASE=http://<サーバー>/api

# ログイン（Cookie を cookie.txt に保存する）
curl -s -c cookie.txt -H "Content-Type: application/json" \
     -d '{"login_id": "admin", "password": "<パスワード>"}' $BASE/auth/login

# 以後は Cookie を付けて呼ぶ
curl -s -b cookie.txt $BASE/staff/me
curl -s -b cookie.txt "$BASE/ops/daily?date=2026-11-10"

# 本文のある操作
curl -s -b cookie.txt -H "Content-Type: application/json" \
     -d '{"reason": "顧客の依頼で延期"}' $BASE/ope/orders/123/hold

# ログアウト
curl -s -b cookie.txt -X POST $BASE/auth/logout
```

### 4.2 API キーで信号を送る

```sh
curl -s -H "Authorization: Bearer ops_xxxxxxxx" -H "Content-Type: application/json" \
     -d '{"type": "data_received", "client_code": "ABCD", "key": "2026-11-10", "received_at": "2026-11-10T08:55:00+09:00"}' \
     http://<サーバー>/api/ope/signals
```

API キーが使えるのはこの呼び出しだけです。ほかの API に付けても 401 になります。

### 4.3 エラーの形

エラーは次の形で返ります（メッセージは英語。画面は主なものを日本語にして出します）。

```json
{"status_code": 403, "error_code": "FORBIDDEN", "message": "..."}
```

| 状態コード | 主な `error_code` | 意味 |
|---|---|---|
| 400 | `BAD_REQUEST` | 今の状態ではできない操作、きまりに合わない値（メッセージに理由） |
| 401 | `UNAUTHORIZED`、`INVALID_CREDENTIALS` | ログインしていない・切れた / ログインID かパスワードが違う |
| 403 | `FORBIDDEN` | ロールが足りない |
| 403 | `STAFF_NOT_ACTIVE` | アカウントが利用開始前・停止中 |
| 403 | `PASSWORD_CHANGE_REQUIRED` | 仮パスワードのまま（`/staff/me`、`/auth/password`、`/auth/logout` だけ使える） |
| 403 | `ACCOUNT_LOCKED` | ログインの失敗が続いてロック中 |
| 403 | `FOUR_EYES` | 自分が提出したステップを承認・差し戻ししようとした |
| 404 | `NOT_FOUND` | 対象がない |
| 409 | `RECORD_ALREADY_EXISTS`、`ORDER_IN_PROGRESS`、`DELETE_FAILED_RECORD_IN_USE` | 重複 / 作業中のオーダーの予定を動かそうとした / 使用中で削除できない |
| 422 | （FastAPI の形式） | 本文の項目が足りない・型が違う |

## 5. 通しの確認シナリオ（QA 向け）

新しい顧客 1 つで、設定から完了までを一通り確かめる手順です。職員は 3 人（業務管理者 + リリース担当、作業者、確認者）を用意します。

| # | 誰が | 操作 | 期待する結果 |
|---|---|---|---|
| 1 | システム管理者 | 職員を 3 人登録し、有効化して仮パスワードを設定（3.2） | 一覧に「仮パスワード」の印 |
| 2 | 各職員 | 仮パスワードでログイン | パスワードの変更の画面になり、変えるまで進めない |
| 3 | 業務管理者 | 顧客を登録（3.3）、業務を 1 つ登録（3.4） | 業務コードが `<顧客コード>0001` |
| 4 | 業務管理者 | SOP の新しい版にステップを 2 つ入れ、明日からで承認（3.5） | 版が「予定」になる |
| 5 | 業務管理者 | 平日毎日のテンプレートを作る（3.7）。締切 = 予定の終了、まもなく = 30 分前 | カレンダーに予定が並び、日次ダッシュボードの行に「未リリース」 |
| 6 | （翌日）リリース担当 | 当日のオーダーを「リリース」（3.11） | 「リリース済」。詳細に SOP の版とステップ 2 つ（待機） |
| 7 | 作業者 | 「開始」→ ステップ 1 を「提出」（3.12） | 「作業中」。ステップ 1 = 確認待ち、ステップ 2 = 未提出 |
| 8 | 作業者 | ステップ 1 を自分で承認しようとする | 承認のボタンが出ない（API なら 403 `FOUR_EYES` か `FORBIDDEN`） |
| 9 | 確認者 | ステップ 1 を「差し戻し」（理由を入れる） | ステップ 1 = 未提出。理由が表示される |
| 10 | 作業者 → 確認者 | ステップ 1・2 を提出し、確認者が両方を承認 | オーダーが自動で「完了」。行の進みが `2/2` |
| 11 | 作業者 | 別の日（未来）のオーダーを開始しようとする | 「開始」が出ない。リリース担当が「予定日前の開始を承認」すると出る |
| 12 | リリース担当 | カレンダーで未来の予定を「変更」（3.10） | 予定とオーダーの日時が動く。詳細の記録に「日時の変更」 |
| 13 | リリース担当 | 未来のオーダーを「取消」（理由を入れる） | オーダーが取消になり、カレンダーからも消える。「取消済みの予定」に出る |
| 14 | — | 締切を過ぎた未完了のオーダーを用意する（所要時間の短いテンプレートで） | 行に「遅れ」。タブ「締切・遅れ」の件数が増える |
| 15 | 誰でも | SLA を開く（3.15） | 完了したオーダーの月に数字が出る。CSV を保存できる |
| 16 | 閲覧者（いれば） | 設定の画面を開く | 見られるが、変更のボタンが出ない |

自動の処理を確かめるとき:

- 業務のリリースの方法を「自動」、時刻を数分後にする → その時刻から 1 分ほどで「リリース済」になる（記録の操作者はシステム）
- 「信号で自動的に完了する」業務を作り、API キーで信号を送る（4.2）→ リリース済のオーダーが完了になる。
  未リリースのうちに送ると「照合できない」としてタブ「信号」に出る

## 6. MVP の制限

| 項目 | 今の状態 |
|---|---|
| 通信 | 社内ネットワークの http だけ（HTTPS・社外からの利用はなし） |
| 通知 | メール・チャットへの通知はない。「まもなく」「遅れ」は画面で確認する |
| 顧客ごとの閲覧制限 | ない。有効な職員はすべての顧客を見られる |
| 営業日カレンダーの作成・週末の変更 | 画面なし（サーバーのスクリプトか API） |
| 年間計画シートの元の表（Excel など）の読み取り | システムは読まない。利用者の側で JSON ファイルに変換して取り込む（3.8） |
| 年間計画シートの削除 | 画面も API もない（日付は「ファイルに合わせる」か 1 件ずつ消せる） |
| 削除したテンプレートの復元 | 画面なし（API `POST /plans/templates/{id}/restore` はある） |
| 依存関係の変更 | 削除して作り直す |
| SOP の承認 | 業務管理者 1 人でできる（承認者を分ける仕組みはない） |
| 信号の受け口 | HTTP の API だけ（ファイルの到着を見張る仕組みは未実装） |
| API の説明画面 | `/api/docs` は使えない。`/api/openapi.json` を見る |
| 職員・顧客の削除 | できない（利用停止・無効にする） |
