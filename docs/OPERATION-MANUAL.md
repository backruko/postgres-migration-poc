# 業務オーケストレーション システム 操作マニュアル（MVP）

このマニュアルは、社内サーバーで動いている MVP について「何ができるか」と「どう操作するか」をまとめたものです。
読む人は、動作を確かめる QA の担当者と、これから運用を担当する職員を想定しています。

- 画面での操作を中心に書き、同じことを API で行う方法を各節の「API」に添えています。
- サーバーの立て方・更新・バックアップは [deploy/README.md](../deploy/README.md)、使い始めの作業は
  [deploy/GO-LIVE.md](../deploy/GO-LIVE.md) を見てください。
- API の正確な項目は `http://<サーバー>/api/openapi.json` で確認できます。

## 1. システムの概要

### 1.1 何をするシステムか

顧客ごとの定例業務について、「いつ行うか」（予定）と「実際にどう進んだか」（オーダー）を管理します。

- 業務ごとの予定をルールから自動で作り、カレンダーと日次ダッシュボードに出す
- 予定 1 件につき 1 件のオーダーを作り、リリース → 開始 → ステップの提出・承認 → 完了 まで記録する
- 手順書（SOP）を版で管理し、オーダーがどの版で作業するかをリリースの時点で固定する
- 締切が近いもの・過ぎたものを知らせ、月ごとの期限内率（SLA）を集計する
- 業務どうしの順番（依存関係）と、顧客側の出来事（ファイルの受領など）を扱う

### 1.2 用語

| 用語 | 意味 |
|---|---|
| 顧客 | 業務の依頼元。4 文字のコードで区別する |
| 業務 | 顧客ごとの仕事の単位。業務コード（顧客コード + 連番 4 桁）は自動で付く |
| SOP | 業務の手順書。版（草稿 → 予定 → 現行 → 過去）とステップを持つ。リリース担当が書いた草稿は、承認を依頼すると「承認待ち」になる |
| 予定テンプレート | 予定を作るルール（毎月 27 日、指定した日、年間計画シートの日付から何日前、など） |
| 予定 | テンプレートから作られた「この日時に行う」1 件 |
| オーダー | 予定 1 件に対する実作業の記録。状態と履歴を持つ |
| ステップ | オーダーの中の手順。SOP の版から、リリースの時点で作られる |
| 営業日カレンダー | 週末と休日の定義。休日に当たった予定の動かし方に使う |
| 信号 | 顧客側の出来事（例: ファイルが届いた）を外部の仕組みが知らせる通知 |

### 1.3 オーダーの状態

```
未リリース → リリース済 → 作業中 → 完了
                 ↘ 保留中（再開すると元の状態に戻る）
   どの状態からでも（完了を除く）→ 取消
```

| 状態 | 意味 |
|---|---|
| 未リリース | 予定はあるが、まだ作業に出していない。予定の変更に追従する |
| リリース済 | 作業に出した。SOP の版とステップがこの時点で固定される |
| 作業中 | 作業者が開始した。ステップを提出・承認できる |
| 保留中 | 一時的に止めている。再開すると止める前の状態に戻る |
| 完了 | すべてのステップが承認された（ステップのないオーダーは作業者が完了にする） |
| 取消 | 取り消した。履歴は残る |

オーダーには状態のほかに次の印が付きます。

| 印 | 意味 |
|---|---|
| 矛盾 | 予定が動いたのに、オーダーが追従できなかった（例: 作業中に休日が追加された）。解決するまでリリース・開始ができない |
| 待ち | 先に終わるべき上流のオーダーがまだ完了していない |
| まもなく | 締切が近い（テンプレートで決めた「何分前」から） |
| 遅れ | 締切を過ぎても完了・取消になっていない |

### 1.4 ロール

1 人が複数のロールを持てます。操作できるのは状態が「有効」の職員だけです。

| ロール | できること |
|---|---|
| 作業者 | オーダーの開始・保留・再開、ステップの提出、ステップのないオーダーの完了・受領、信号の対応 |
| 確認者 | ステップの承認・差し戻し（自分が提出したステップは不可） |
| リリース担当 | リリース、予定日前の開始の承認、依存関係を待たない開始の承認、SOP の版の指定、取消、矛盾の解決、カレンダーでの予定の変更、予定テンプレートの変更の下書き（作成・変更・削除の依頼。業務管理者の承認で反映）、SOP の草稿（作成・編集・削除・承認の依頼。業務管理者の承認で使われる）、業務のリリース設定の変更（すぐに効く。履歴に残る）、シートの取り込みの内容の確認（取り込みはできない） |
| 業務管理者 | 設定の変更すべて（顧客・業務・SOP・テンプレート・休日・依存関係）、テンプレートの下書きと SOP の草稿の承認・差し戻しと、リリース担当と同じオーダーの操作（予定日前の開始の承認を除く） |
| 閲覧者 / 監査担当 | 参照のみ（監査担当は職員の一覧も見られる） |
| システム管理者 | 職員アカウントの管理（登録・ロール・有効化・仮パスワード・API キー）。業務の操作は含まない |
| 信号の送信 | 外部の仕組み用。API キーで信号を送るだけ |
| システム連携（読み取り） | 外部の仕組み用（mfa のアダプターなど）。API キーで、まもなく・遅れのオーダーと日次の状況を読むだけ。人のロールと一緒には持てず、パスワードも持てない（画面にはログインできない） |

**担当顧客（顧客の範囲）。** 職員に担当顧客を決めると、その顧客だけを扱う職員になります（決めなければ全顧客。今までどおり）。
ロールは「何ができるか」、担当顧客は「どの顧客か」を決めます（例: 担当顧客 A の作業者は、A のオーダーだけを開始できる）。

- ほかの顧客の業務・予定・オーダー・シート・信号は、一覧に出ず、リンクを開いても「見つかりません」になります
- 全顧客に共通の設定は使えません: 顧客の登録・変更、休日カレンダーの変更、職員の画面（設定のメニューにも出ません）。
  顧客の一覧と休日カレンダーは見られます
- 業務管理者・リリース担当なら、担当顧客の業務・SOP・テンプレート・シートは今までどおり変えられます
- システム管理者には担当顧客を付けられません（職員の画面は全顧客に共通のため）
- 右上の名前のメニューに、自分の担当顧客が出ます

### 1.5 画面の一覧

| 画面 | 場所 | 内容 |
|---|---|---|
| ログイン | `/login` | ログインID とパスワード |
| カレンダー | ナビ「カレンダー」 | 顧客ごとの月の予定。予定の変更・取消・臨時の予定 |
| 日次ダッシュボード | ナビ「日次ダッシュボード」 | 全顧客のその日の予定とオーダー。タブ: 予定 / 締切・遅れ / 信号 / 通知の失敗。届かなかったアラームがあると、ナビに赤い件数が出る（3.17） |
| SLA | ナビ「SLA」 | 顧客 × 月の期限内率。CSV の出力 |
| 出来事・通知 | ナビ「出来事・通知」 | タブ「出来事」: 締切の監視が記録した「遅れ」「まもなく」とテスト送信。タブ「通知」: 作った通知と、宛先ごと・1 回ごとの送信の記録（参照のみ。QA・運用の確認用） |
| ワーカーの状態 | ナビ「ワーカーの状態」 | 毎分の自動処理（ワーカー）が動いているか、1 日ごとの心拍・エラー・途切れと期間の判定（参照のみ。並行稼働の承認の記録。3.19） |
| 設定 | ナビ「設定」のメニュー | 顧客 / 業務 / SOP / 予定テンプレート設定 / 承認待ち / 年間計画シート / 休日カレンダー / 業務の依存関係 / 通知の設定 / 職員。業務管理者には承認待ち（テンプレートの下書きと SOP の草稿の合計）の件数が出る |

右上の自分の名前のメニューに「パスワードを変更」と「ログアウト」があります。

### 1.6 自動で動く処理

| 処理 | いつ | 内容 |
|---|---|---|
| 自動リリース | 毎分 | リリースの方法が「自動」の業務で、決めた時刻を過ぎた未リリースのオーダーをリリース済にする |
| 締切の監視 | 毎分 | 締切を過ぎたオーダー（遅れ）と「まもなく」の時刻を過ぎたオーダーを、出来事として記録する（3.16） |
| 通知の振り分け・配信 | 毎分 | 出来事を通知のルール（3.18）に当てはめ、宛先にメールで送る。届かなければ 1・5・15・60 分後に送り直す。メールサーバーの設定がないと送らない（`deploy/README.md`） |
| 予定の生成 | 毎日 00:05 | すべてのテンプレートの予定を約 90 日先まで作り足す。新しい予定にはオーダーも作る |
| バックアップ | 毎日 01:00 | データベースを `/srv/ops/backups/` に保存する（14 日分） |
| 画面の更新 | 2 分ごと | 日次ダッシュボードが開いている間、自動で読み直す。承認待ちの件数（業務管理者）と承認待ちの一覧、届かなかったアラームの件数（ナビの赤い件数・帯）も |

## 2. 前提条件

### 2.1 画面を使うとき

- 社内ネットワークからブラウザで `http://<サーバーの IP アドレス>/` を開く（http。社外からは届きません）
- 職員アカウントがあり、状態が「有効」で、パスワードが設定されていること
- 操作に合ったロールを持っていること（1.4）

アカウントは システム管理者 が 設定 → 職員 で作ります（3.2）。最初の管理者だけはサーバーでコマンドから作ります
（[deploy/README.md](../deploy/README.md) の 3.9）。

### 2.2 ログインのきまり

| 項目 | きまり |
|---|---|
| パスワード | 8〜128 文字。前後に空白を入れない。ログインID と同じものは不可 |
| 仮パスワード | システム管理者が設定したパスワード。最初のログインで本人が変えるまで、ほかの画面・API は使えない |
| ロック | 5 回続けて間違えると 15 分間ログインできない（システム管理者が仮パスワードを設定し直すと解除される） |
| ログインの期限 | 12 時間操作がないと切れる。操作していても最長 7 日 |
| ログインが切れるとき | ログアウト、利用停止、パスワードの変更・再設定（変更した本人の今の画面は残る） |

### 2.3 API を使うとき

API は画面と同じサーバーの `/api` の下にあります（例: `http://<サーバー>/api/ops/daily`）。
本文は JSON、文字コードは UTF-8、日時は ISO 8601（タイムゾーン付き）です。

認証は 2 通りです。

| 方法 | 使う場面 | やり方 |
|---|---|---|
| ログインの Cookie | 人の操作と同じことをする API すべて | `POST /api/auth/login` が返す Cookie `ops_session` を、以後の呼び出しに付ける |
| API キー | 機械用のアカウントの、決まった呼び出しだけ: 「信号の送信」は `POST /api/ope/signals`、「システム連携（読み取り）」は `GET /api/ops/attention`・`GET /api/ops/schedule-feed`・`GET /api/ops/daily`・`GET /api/staff/me` | ヘッダー `Authorization: Bearer <キー>`。キーは システム管理者 が機械用のアカウントに発行する（3.2）。ほかの呼び出しに付けると 401 |

ログインなしで呼べるのは `POST /auth/login`、`POST /auth/logout`、`GET /openapi.json` だけです。
具体的な呼び方とエラーの形は 4. を見てください。

## 3. 機能ごとの手順

各節の「必要なロール」は、その操作をする人に必要なものです。見るだけなら、有効な職員であれば誰でも見られます
（職員の一覧だけは システム管理者・業務管理者・監査担当）。

### 3.1 ログイン・パスワードの変更・ログアウト

**ログイン**

1. `http://<サーバー>/` を開く。ログインしていなければログイン画面になる
2. ログインID とパスワードを入れてログインする
3. 仮パスワードのときは「パスワードを変更してください」の画面になる。今のパスワードと新しいパスワード（2 回）を入れる

**パスワードの変更**: 右上の名前 →「パスワードを変更」。

**ログアウト**: 右上の名前 →「ログアウト」。

主なエラー: 「ログインIDまたはパスワードが違います。」/ ロック中（解除される時刻が出る）/ アカウントが利用開始前・停止中。

**API**

| 操作 | 呼び出し |
|---|---|
| ログイン | `POST /auth/login` `{"login_id": "...", "password": "..."}` → 職員の情報 + Cookie |
| 自分の情報 | `GET /staff/me` |
| パスワードの変更 | `POST /auth/password` `{"current_password": "...", "new_password": "..."}` |
| ログアウト | `POST /auth/logout` |

### 3.2 職員の管理

必要なロール: システム管理者。画面: 設定 → 職員。

**職員を登録する**

1. 「職員を登録」を押し、ログインID・氏名・メールアドレス（任意）・ロールを入れる
2. 登録した直後の状態は「利用開始前」。行の「有効化」を押す
3. 行の「仮パスワード」を押してパスワードを決め、本人に伝える（一覧に「仮パスワード」の印が付く）
4. 本人が最初のログインで自分のパスワードに変える

**そのほかの操作**

| したいこと | 操作 |
|---|---|
| 氏名・メール・ロールを変える | 行の「編集」（自分のシステム管理者ロールは外せない） |
| 担当顧客を決める | 行の「編集」→「担当顧客」で顧客を選ぶ（複数可。空 = 全顧客）。システム管理者のロールと一緒には付けられない。新しく選べるのは有効な顧客だけ。次の操作から効く |
| 使えなくする / 戻す | 「利用停止」/「再開」（自分の行は不可。停止するとログインも切れる。ロールは残る） |
| パスワードを忘れた・ロックされた | 「仮パスワード」で設定し直す（自分自身には不可。自分の分は右上のメニューから） |
| 機械用のアカウントのキーを発行する | 「信号の送信」か「システム連携（読み取り）」の職員の行で「API キー」→ 用途を入れて「発行」。画面にそのキーで呼べるものが出る。**キーの全文はこのときだけ表示される**ので控える。不要になったら「取り消す」（すぐに使えなくなる） |
| 外部の仕組みに読み取りだけを許す（mfa のアダプターなど） | 「職員を登録」でロールに「システム連携（読み取り）」だけを選ぶ（選ぶと人のロールは選べなくなる。パスワードは設定しない）→「有効化」→「API キー」で発行。一部の顧客だけを読ませるなら「担当顧客」を選ぶ |

職員は削除できません（履歴に名前が残るため）。使わなくなったら利用停止にします。
一覧の印: パスワード未設定 / 仮パスワード / ロック中。

**API**

| 操作 | 呼び出し |
|---|---|
| 一覧 / 1 件 | `GET /staff/`、`GET /staff/{id}` |
| ロールの一覧 | `GET /staff/roles` |
| 登録 | `POST /staff/` `{"login_id", "name", "email", "roles": ["operator", ...]}` |
| 氏名・メール | `PATCH /staff/{id}` |
| ロール | `PUT /staff/{id}/roles` `{"roles": [...]}` |
| 担当顧客 | `PUT /staff/{id}/clients` `{"client_codes": ["MOCK", ...]}`（空の配列 = 全顧客。職員の応答の `client_codes`） |
| 状態 | `PUT /staff/{id}/status` `{"status": "active"}`（または `"suspended"`） |
| 仮パスワード | `PUT /staff/{id}/password` `{"password": "..."}` |
| API キー | `GET /staff/{id}/api-keys`、`POST /staff/{id}/api-keys` `{"label": "..."}`、`POST /staff/api-keys/{key_id}/revoke` |

ロールのコード: `operator` 作業者 / `checker` 確認者 / `releaser` リリース担当 / `admin` 業務管理者 / `viewer` 閲覧者 /
`auditor` 監査担当 / `system_admin` システム管理者 / `signal_sender` 信号の送信。

### 3.3 顧客

必要なロール: 業務管理者。画面: 設定 → 顧客。

1. 「顧客を登録」を押し、顧客コード（英数字 4 文字。大文字になる。**あとで変えられない**）と顧客名を入れる
2. 名前を直すときは行の「名前を変更」
3. 取引が終わった顧客は「無効にする」。一覧や選択肢に出なくなり、業務・シートを新しく作れなくなる（履歴は残る）。戻すときは「有効にする」

顧客は削除できません。有効な業務が残っている顧客は無効にできません（先に業務を削除する）。

**API**: `GET /clients/?include_inactive=true`、`POST /clients/` `{"code", "name"}`、`PATCH /clients/{id}` `{"name"}`、
`POST /clients/{id}/deactivate`、`POST /clients/{id}/activate`。

### 3.4 業務と業務の設定

必要なロール: 業務管理者。ただし業務の設定のうちリリースの 3 項目（方法・何日前・時刻）は、リリース担当も変えられる（下の「リリースを編集」）。
画面: 設定 → 業務（顧客を選ぶ）。

**業務を登録する**

1. 顧客を選び、「業務を登録」を押す。業務コードは自動で決まり、画面に表示される（登録後は変えられない）
2. 業務名、管理者のメールアドレス（任意）、説明（任意）を入れる

**業務の設定を決める**: 業務の行の「予定テンプレート・業務の設定」→ 業務の設定の「編集」。
リリースの 3 項目（方法・何日前・時刻）は**リリース担当も変えられます**: 業務の設定の「リリースを編集」（リリースの項目だけのフォーム）。
保存するとすぐに効きます（まだリリースされていないオーダーの自動リリースの日時も変わります）。

| 項目 | 選択肢 | 意味 |
|---|---|---|
| リリースの方法 | 手動（リリース担当が承認）/ 自動（指定の時刻に） | 自動にすると、決めた時刻にシステムがリリースする |
| 自動リリース: 予定日の何日前 | 0〜30（0 = 当日） | |
| 自動リリースの時刻 | 既定 03:00（日本時間） | |
| 実行のしかた | SOP のステップで作業する / 顧客側の出来事（ステップなし） | 後者はファイルの受領など、ステップのない業務 |
| 完了のしかた | 作業者が受領を記録する / 信号で自動的に完了する | 「信号で自動」は「顧客側の出来事」のときだけ選べる |
| 信号の種類 | 文字列 | 「信号で自動」のとき必須。送信側と同じ値にする。同じ顧客の中で重複不可 |

**リリース設定の履歴**: 業務の設定の「履歴」（誰でも）。いつ・だれが・変更前 → 変更後が新しい順に出ます。
業務管理者の「編集」で変えたものも、リリース担当の「リリースを編集」で変えたものも載ります（値が変わったときだけ。2026-11-11 より前の変更は記録がありません）。

**削除と復元**: 行の「削除」/「元に戻す」。次のどれかがあると削除できません（理由が表示されます）:
依存関係の定義、有効な予定テンプレート、完了・取消になっていないオーダー。

**API**

| 操作 | 呼び出し |
|---|---|
| 一覧 | `GET /biz/?client_code=XXXX&include_deleted=true` |
| 登録 | `POST /biz/` `{"client_code", "name", "manager_email", "description"}` |
| 編集・業務の設定 | `PATCH /biz/{id}`（`release_mode`、`release_time`、`release_days_before`、`execution_type`、`completion_mode`、`signal_type` など、変える項目だけ） |
| リリース設定だけ（リリース担当も） | `PATCH /biz/{id}/release` `{"release_mode": "automatic", "release_time": "05:30:00", "release_days_before": 1}`（変える項目だけ。ほかの項目は 422） |
| リリース設定の履歴 | `GET /biz/{id}/release-changes` |
| 削除 / 復元 | `DELETE /biz/{id}`、`POST /biz/{id}/restore` |

### 3.5 SOP（手順書の版とステップ）

必要なロール: 草稿の作成・編集・削除と承認の依頼はリリース担当と業務管理者、承認・差し戻し・予定の取消は業務管理者。
画面: 設定 → SOP（業務を選ぶ）。左に版の一覧、右に選んだ版のステップ。版の題名の下に、作った人と最後に直した人・日時が出ます。

版の状態:

| 状態 | 意味 | 編集 |
|---|---|---|
| 草稿 | 作成中 | できる |
| 予定 | 承認済みで、使い始めの日がまだ来ていない | できない（承認を取り消せば草稿に戻る） |
| 現行 | 今使われている | できない |
| 過去 | 次の版に替わった | できない |

**新しい版を作って使い始める**

1. 「新しい版」を押し、タグ（例: `v1.1.0`）を決める。最新の承認済みの版があればその内容が写される（最初は空）
2. 「ステップを追加」で手順を入れる
   - 手順（題名）、内容
   - 含める条件: 毎回 / 指定した月だけ / 週の最初の予定だけ
   - 「承認で次へ」: チェックすると、このステップが**承認**されるまで次のステップが開かない（付けなければ**提出**で次が開く）
3. 並べ替えは ↑ / ↓、直すときは「編集」、消すときは「削除」。番号が飛んだら「番号を振り直す」
4. 「承認…」を押し、使い始めの日を選ぶ（**最も早くて明日**。その日の 00:00 日本時間から有効）
   - 画面に、影響を受けるオーダーが 3 つに分けて出る: 新しい版を使うオーダー / 指定した版のまま / リリース済み（固定した版のまま）
   - 「ひとこと」（任意）は版の履歴に残る。自分の草稿を承認するときは、その旨が表示され、履歴にも残る
5. 承認すると版は「予定」になり、使い始めの日に「現行」になる。それまでの現行の版は前日までになる

**リリース担当が書いた草稿を承認してもらう**

1. リリース担当は、上の 1〜3 と同じように草稿を作って直す（「承認…」の代わりに **「承認を依頼」** が出る）
2. 「承認を依頼」を押す。版の一覧と題名に **「承認待ち」** が付き、だれも直せなくなる（業務管理者も同じ）
3. 直したいときは **「取り下げる」**（依頼した本人か業務管理者）。草稿に戻る
4. 業務管理者は、ナビの「設定」の件数か、設定 → **承認待ち** の「SOP の草稿」で気づく。行の「開く」でその版を開き、
   ステップを見て **「承認…」**（上の 4）か **「差し戻す…」**（理由は必須）を押す
5. 差し戻すと草稿に戻り、書いた人が直してもう一度依頼できる。理由は「履歴」で読める

**履歴**: 版の「履歴」で、作成（どの版を写したか）・承認の依頼・取り下げ・差し戻し（理由）・承認（使い始めの日・ひとこと・自分の草稿か）・承認の取消が、
いつ・だれが付きで新しい順に出ます。ステップの 1 つずつの編集は出ません（題名の下の「最終編集」に最後の人と日時）。2026-11-11 より前の版には記録がありません。

きまり:

- ステップが 1 つもない草稿は承認も依頼もできない
- 承認を依頼中の草稿は、タグ・ステップの変更も削除もできない（取り下げるか、承認・差し戻しを待つ）
- 業務管理者は、依頼の無い草稿もそのまま承認できる（自分で書いた草稿も）
- 「予定」の版は同時に 1 つだけ。別の版を承認するには、先の「予定を取り消す」か、使い始めの日を待つ
- 「予定を取り消す」は使い始めの日の前だけ。その版を指定・固定しているオーダーがあると取り消せない
- **リリース済みのオーダーは、あとから版が替わっても変わらない**（リリースの時点の版とステップのまま）
- 使い始めの日より前の予定のオーダーは、その日に有効な版で作業する。有効な版がない日のオーダーはステップなしでリリースされる

**API**

| 操作 | 呼び出し |
|---|---|
| 版の一覧 | `GET /biz/{biz_id}/versions?include_drafts=true` |
| 版とステップ | `GET /biz/versions/{version_id}` |
| 新しい版（写して作る） | `POST /biz/{biz_id}/versions/clone` `{"version_tag": "v1.1.0"}` |
| タグを変更 / 草稿を削除 | `PATCH /biz/versions/{id}`、`DELETE /biz/versions/{id}` |
| ステップの追加 | `POST /biz/versions/{id}/steps` `{"title", "content", "condition": {"type": "always"}, "is_blocking": false}` |
| ステップの編集 / 削除 | `PATCH /biz/steps/{step_id}`、`DELETE /biz/steps/{step_id}` |
| 並べ替え | `PUT /biz/versions/{id}/steps/order` `{"step_ids": [3, 1, 2]}` |
| 影響の確認 | `GET /ope/sop-impact?biz_id=1&effective_date=2026-11-20` |
| 承認 | `POST /biz/{biz_id}/versions/{draft_id}/approve` `{"effective_date": "2026-11-20", "note": "任意"}` |
| 予定を取り消す | `POST /biz/{biz_id}/versions/{version_id}/cancel` |
| 承認を依頼 / 取り下げる | `POST /biz/versions/{id}/submit`、`POST /biz/versions/{id}/withdraw` |
| 差し戻す | `POST /biz/versions/{id}/reject` `{"reason": "手順 2 が足りない"}` |
| 版の履歴 | `GET /biz/versions/{id}/events` |
| 承認待ちの草稿（全業務）/ 件数 | `GET /biz/sop-drafts/submitted?client_code=XXXX`、`GET /biz/sop-drafts/submitted/count` |

条件の書き方: `{"type": "always"}` / `{"type": "month_in", "months": [3, 9]}` / `{"type": "first_in_week"}`。

### 3.6 休日カレンダー

必要なロール: 業務管理者。画面: 設定 → 休日カレンダー（カレンダーと年を選ぶ）。

1. 「日本の祝日を取り込む」で、その年の祝日（振替休日・国民の休日を含む）をまとめて登録する
2. 会社や銀行の休業日（例: 12/31、1/2、1/3）は「休日を追加」で足す
3. 名前の変更・削除は行の操作から

きまり:

- **今日より前の休日は変えられない**（実績と食い違うため）
- 休日を足す・消すと、そのカレンダーを使うテンプレートの**今日以降の予定が作り直される**（人が変更した予定はそのまま）。
  オーダーも追従する（追従できないものには「矛盾」が付く）
- 祝日は法律の規定から計算している。内閣府の発表と違うときは取り込んだあとで直す

カレンダーそのものを作る画面はありません。最初のカレンダー（`JP_BANK` 銀行営業日、土日休み）はサーバーで
`scripts/setup_calendar.py` を 1 回動かして作ります（[deploy/GO-LIVE.md](../deploy/GO-LIVE.md) の B）。

**API**: `GET /plans/calendars`、`GET /plans/calendars/{id}/holidays`、
`POST /plans/calendars/{id}/holidays` `{"holidays": [{"holiday_date": "2026-12-31", "name": "年末休業"}]}`、
`DELETE /plans/calendars/{id}/holidays/2026-12-31`。

### 3.7 予定テンプレート

必要なロール: 業務管理者（作成・変更・削除を直接。下書きの承認・差し戻し）、リリース担当（作成・変更・削除の下書き。下の「下書きと承認」）。
画面: 設定 → 予定テンプレート設定（業務を選ぶ）。

**テンプレートを作る**: 「新規作成」を押して次を決める。

| 項目 | 内容 |
|---|---|
| 種類 | 繰り返しルール / 顧客指定日 / 年間計画シート |
| 予定名、分類、表示色・アイコン | カレンダーでの見え方。分類（定例 / 不定期 / スペシャル）は、開始の知らせ（下）を出す作業かどうかにも使う |
| 開始時刻に知らせる | オンなら、分類が不定期・スペシャルのとき、予定の開始の時刻に「始めて」と知らせる作業になる（外の仕組みへ渡す開始の時刻表 `GET /api/ops/schedule-feed` に載る）。ファイルの到着など、外からの合図を待って始める作業はオフにする。新しいテンプレートの初期値は、業務の実行のしかたが「顧客側の出来事」ならオフ、ほかはオン。一覧では、知らせる作業に「開始を知らせる」、オフの作業に「知らせない」の印が付く。変えても予定は作り直されない |
| 開始時刻、所要時間（分）、タイムゾーン | 予定の時間帯 |
| 起点日、繰り返しルール（RRULE） | 種類が繰り返しルールのとき。例: `FREQ=MONTHLY;BYMONTHDAY=27`、`FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR` |
| 指定日 | 種類が顧客指定日のとき。日付を並べる |
| 年間計画シート、参照するマーカー、基準日のずれ、日数の数え方、時刻のずれ | 種類が年間計画シートのとき。シートの日付から「3 営業日前」などを決める |
| 営業日カレンダー、非営業日に当たった場合 | 休日も実施 / 休日はスキップ / 翌営業日 / 前営業日 / 翌営業日（月をまたぐ場合は前営業日）/ 前営業日（月をまたぐ場合は翌営業日） |
| 締切の決め方 | 予定の終了（開始時刻 + 所要時間）/ 開始から（何分後）/ 固定の時刻（予定日の何日後の何時） |
| 締切の何分前に「まもなく」を出すか | 0 = 出さない |

作ると、すぐに先の予定（約 90 日先まで、少なくとも次の 1 件）ができ、**予定ごとに未リリースのオーダーができます**。
作る前に「予定を確認」を押すと、その内容でできる予定を月ごとの小さなカレンダーで見られます（任意。何も保存されません）。

**変更したとき**

- 時刻・ルール・休日の扱いなどを変えると、**未来の予定だけ**が作り直される。過去の予定と、人が変更・取消した予定はそのまま
- **オーダーが完了・作業中の予定も、そのまま残る**（終わった作業・始まった作業の予定は動かさない。オーダーとつながったまま、今の日時で表示される）。
  今日の予定で、元の時刻がもう過ぎているものも動かない
- その場合は、「保存する」を押すと先に **「保存の前の確認」** が開く（下の「保存の前の確認」）。名前・締切・表示だけの変更は、そのまま保存される
- 締切の項目を変えると、**未リリースのオーダーだけ**に反映される（リリース済み以降は変わらない）
- 削除すると未来の予定は消え、未リリース・リリース済のオーダーは取消になる。過去は残る

一覧の「次の予定」が空で警告の印が付いているテンプレートは、この先 2 年に予定がありません（ルールや指定日を見直す）。

**保存の前の確認**

テンプレートを変えると、予定とオーダーがすぐに動きます。保存する前に、何が起きるかを確かめるための画面です。
システムが実際の保存を試しに行い、結果を読み取ってから取り消すので、**表示される内容は、保存したときに起きることと同じ**です
（この画面を開いただけでは、何も保存されません）。

1. テンプレートの「編集」で項目を変えて「保存する」。日付に関わる変更なら、確認の画面が開く
2. 上の要約を読む:

   | 表示 | 意味 |
   |---|---|
   | 増える / 無くなる / 日時が変わる | 予定の違い。曜日や日にちのルールを変えたときは、元の日が「無くなる」、新しい日が「増える」になる |
   | 人が変更・追加した予定 N 件は、そのまま残ります | 1 日だけ動かした・取り消した予定は、テンプレートを変えても変わらない |
   | オーダー N 件の日時が変わります（うちリリース済み・保留中 n 件） | 予定に追従するオーダー。リリース済みのものは、現場がもう見ている |
   | オーダー N 件が取消になります | 予定が無くなるオーダー（未リリース・リリース済） |
   | オーダー N 件が「矛盾」になります | 保留中のオーダーの予定が無くなるときなど、自動では決めないもの。保存の後、日次ダッシュボードで人が判断する（3.11） |
   | オーダーが新しく N 件できます | 増える予定の分 |

3. 月ごとのカレンダーで日を確かめる。色の意味は上の凡例のとおり（無くなる日は取り消し線、人が変更した日は破線の枠）。日にマウスを置くと時刻が出る
4. 範囲は 3 か月（既定）/ 6 か月 / 12 か月を選べる。もう作られている予定の範囲のほうが長いときは、そこまで表示される
5. 下の一覧を開くと、日付と、影響するオーダー（今の状態・今の予定・保存するとどうなるか）を 1 件ずつ見られる
6. よければ「この内容で保存する」。直すときは「戻って直す」

知っておくこと:

- **動かない予定**: オーダーが完了・作業中の予定と、今日の予定で元の時刻がもう過ぎているものは、変更の対象にならない
  （確認の件数にも入らない）
- 業務管理者が直接保存するときの確認には、顧客指定日の指定日の追加・削除は含まれない（画面にその旨が出る）。下書きの承認の確認には含まれる
- この業務を待っている別の業務のオーダー（依存関係）は、影響するオーダーの一覧には出ない
- 確認を取れなかったとき（エラー）は、保存されない

**下書きと承認（リリース担当が書き、業務管理者が承認する）**

予定テンプレートの変更は、リリース担当が **下書き** として書き、業務管理者が **承認** するとすぐに反映されます
（反映の日を予約する仕組みはありません）。業務管理者は、これまでどおり直接保存できます。
下書きの間は、テンプレートも予定もオーダーも今のままです。

リリース担当がすること:

1. テンプレートの行の「変更を下書き」、または「新しいテンプレートを下書き」を押す。業務管理者と同じフォームが開く
   （上に「保存すると下書きになります」と出る）
2. 項目を変えて「下書きとして保存」。日付に関わる変更なら、先に上の「保存の前の確認」が開き、「この内容で下書きを保存」で保存する。
   項目の変更と指定日の追加・削除は、1 つの下書きにまとめて保存される
3. 削除したいテンプレートは「削除を依頼」（削除の下書きができる。承認されるまで消えない）
4. 下書きのあるテンプレートには **「承認待ち」** の印が付き、だれも変更・削除できなくなる（業務管理者の直接の保存も同じ）。
   1 つのテンプレートに置ける承認待ちの下書きは 1 つだけ
5. 「下書きを見る」で中身（項目ごとに 今 → 下書きの内容）を確かめられる。書いた本人は、承認されるまで
   **「直す」**（下書きの中身でフォームが開き、保存すると下書きが置き換わる）と **「取り下げる」** ができる。
   直した結果が今の設定と同じになったときは、「この下書きを取り下げますか？」と聞かれる
6. 業務を選ぶと、テンプレートの一覧の上に **「変更依頼」** の欄が出る: その業務の承認待ちの下書き（新しいテンプレートの下書きを含む）と、
   自分の下書きのうち 30 日以内に決まったもの（差し戻しの理由つき）

業務管理者がすること:

1. ナビの「設定」に、承認待ちの件数が出る（業務管理者だけ。テンプレートの下書きと SOP の草稿（3.5）の合計。2 分ごとと、
   だれかが下書きを保存・承認したときに更新）
2. 設定 → **承認待ち** を開く。上の「予定テンプレートの下書き」に、全業務の承認待ちの下書きが古い順に並ぶ（顧客で絞り込める。
   下の「SOP の草稿」は 3.5）。業務の名前から、その業務の
   予定テンプレート設定へ移れる
3. 「見る」で下書きの窓を開く。**今のデータで当てはめたら起きること**（保存の前の確認と同じ: 予定の違いとオーダーへの影響）が
   自動で出る。下書きを書いた後に休日やシートの日付が変わっていても、ここで反映される。確認が終わるまで承認はできない
4. よければ **「承認する」**（ひとことは任意）。すぐにテンプレートに反映され、未来の予定とオーダーが動く。
   直すところがあれば **「差し戻す」**（理由は必須。書いた人の「変更依頼」の欄に出る）。業務管理者は下書きを直さない
5. 自分の下書きも承認できる（その旨が記録に残る）。承認のときにエラーになったら（参照するシートが無いなど）、何も変わらず、
   下書きは承認待ちのまま残る

**変更履歴**: テンプレートの行の「履歴」で、そのテンプレートの変更を新しい順に見られる（だれでも）。承認された下書き、
差し戻し・取り下げ、業務管理者の直接の保存が残る。承認された変更は「変更前 → 変更後」で、その時に何が変わったかが分かる。
記録は、下書きと承認の仕組みができた後の変更からです。

知っておくこと:

- 承認待ちの間も、カレンダーでの 1 件ずつの変更・取消・臨時の予定、年間計画シートと休日の変更はできる（テンプレートの設定ではないため）。
  ただし、そのテンプレートが参照するシートのマーカーの名前は変えられない（3.8）
- 承認待ちの下書きがある業務は削除できない（先に承認・差し戻し・取り下げをする）
- 年間計画シートの取り込みには下書きはない（業務管理者が直接取り込む。リリース担当は取り込みの内容の確認まで）
- 下書きを見る・承認待ち・履歴は、ログインしている職員ならだれでも見られる。承認・差し戻しは業務管理者だけ

**API**: `GET /plans/templates?biz_id=1`、`POST /plans/templates`、`PATCH /plans/templates/{id}`、`DELETE /plans/templates/{id}`、
指定日の追加・削除 `POST /plans/templates/{id}/dates` `{"dates": ["2026-12-01"]}`、`DELETE /plans/templates/{id}/dates/2026-12-01`。
作成の本文は種類ごとに項目が違うため、`/api/openapi.json` の `POST /plans/templates` を見てください。

保存の前の確認（リリース担当・業務管理者。何も保存しない。`months` は 1〜12、既定 3）:

- 変更: `POST /ops/templates/{id}/preview?months=3`、本文は `PATCH /plans/templates/{id}` と同じ（例: `{"start_time": "14:00:00"}`）。
  返るもの: `generation_changed`（false なら日付は変わらない）、`occurrences`（変更の後の予定）、`added` / `removed` / `moved`、
  `manual_unchanged`、`orders_total`、`orders_created`、`order_effects`（`rescheduled` / `canceled` / `conflict` と、今の状態）
- 新規: `POST /ops/templates/preview?months=3`、本文は `POST /plans/templates` と同じ。返るもの: `occurrences`、`orders_created`
- 入力の誤りは、実際の変更・作成と同じエラーになる

下書きと承認:

- 下書きを作る（リリース担当・業務管理者）: `POST /plans/template-changes`。本文は `kind` で形が変わる:
  `{"kind": "update", "template_id": 12, "changes": {"start_time": "10:00:00"}, "add_dates": [], "remove_dates": []}`、
  `{"kind": "create", "template": { POST /plans/templates と同じ本文 }}`、`{"kind": "delete", "template_id": 12}`。
  本物の保存と同じ処理で確かめられ、何も変えない下書きは 400
- 書いた本人が直す・取り下げる: `PUT /plans/template-changes/{id}`（中身をまるごと置き換える）、`POST /plans/template-changes/{id}/withdraw`
- 業務管理者が承認・差し戻す: `POST /plans/template-changes/{id}/approve` `{"note": "…"}`（本文は省略可）、
  `POST /plans/template-changes/{id}/reject` `{"reason": "…"}`（理由は必須）
- 今のデータで当てはめたら起きること（リリース担当・業務管理者。何も保存しない）: `POST /ops/template-changes/{id}/preview?months=3`。
  新規作成は `create`、変更・削除は `change` に、上の確認と同じ形で返る
- 読む（だれでも）: `GET /plans/template-changes?status=draft&biz_id=&template_id=&drafted_by=&limit=`（承認待ちは古い順）、
  `GET /plans/template-changes/count`（既定は承認待ちの件数）、`GET /plans/template-changes/{id}`、
  `GET /plans/templates/{id}/changes`（変更履歴、新しい順）。テンプレートの応答の `pending_change_id` は承認待ちの下書き

### 3.8 年間計画シート

顧客の年間計画（例: 振込日、締め日）の日付を持ち、テンプレートがそこから「何日前」と計算するためのものです。
1 つのシートに、日付の種類（マーカー）がいくつも入ります。必要なロール: 見るのは誰でも、変更・取り込みは業務管理者。リリース担当は、取り込みの内容の確認までできる。画面: 設定 → 年間計画シート（顧客を選ぶ）。

**役割の分担:** 顧客から届く表（Excel など）をシステムは読みません。表から決まった形の JSON ファイルへの変換は、**利用者の側**（システムの外）で行い、
システムはその JSON ファイルだけを受け取ります。

#### シートを取り込む（新しく作る・日付を足す）

1. 設定 → 年間計画シート → 顧客を選ぶ →「シートを取り込む」
2. JSON ファイルを置くか、クリックして選ぶ。読めないファイル・項目の足りないファイルは、理由がすべて表示されて止まる
3. 表示を確かめる: 顧客コード、シート名（「新しく作る」か「既にあるシートを更新」か）、期間、マーカーと日付の件数、「取り込むと: …」の件数
4. 既にあるシートの場合は、取り込み方を選ぶ:

   | 取り込み方 | 動き | 使う場面 |
   |---|---|---|
   | 追加だけ（既定） | ファイルにある日付で、まだ無いものを追加する。今ある日付は消さない。シートの期間は、今のシートとファイルの両方を含むように広がる | **次の年の分が届いたとき**（その年だけのファイルでよい）、日付の追加 |
   | ファイルに合わせる | 追加に加えて、ファイルに無い日付を削除し、期間もファイルのとおりにする | 顧客が表を出し直し、無くなった日付を消したいとき |

5. 「取り込む」。結果（追加したマーカー・説明を変えたマーカー・追加した日付・削除した日付・予定を作り直したテンプレート）が表示される

**リリース担当ができること（確認だけ）**: 「取り込みの内容を確認」を押すと同じ画面が開き、ファイルを選んで、上の 2〜4（内容の表示・
取り込み方ごとの「取り込むと: …」の件数・警告）までを見られる。取り込みのボタンは出ない。ここまではブラウザの中の計算で、ファイルは
サーバーに送られない。よければ、そのファイルと取り込み方を業務管理者に伝え、業務管理者が取り込む。

決まり:

- 同じシートかどうかは **顧客コード + シート名** で決まる。同じなら更新、無ければ新しく作る。毎年同じシート名を使う（テンプレートは 1 つのシートのマーカーを参照するため、年ごとに別のシートにしない）
- 同じファイルをもう一度取り込んでも、何も変わらない
- 全体が 1 つのまとまりで、エラーのときは何も反映されない
- **人が変更・追加・取消した日付は、どちらの取り込み方でも変わらない**（人が取り消した日付は、ファイルにあっても戻らない）
- 「ファイルに合わせる」では、**ファイルに日付が 1 件も無いマーカーは日付がすべて消える**（取り込む前に、マーカー名と件数が警告に出る）。全マーカーの全期間の日付を入れたファイルで行う
- ファイルに無いマーカーそのものは消えない（テンプレートが参照しているかもしれないため）
- ルールで日付を作るマーカーの日付は、取り込めない（ファイルに入っていると止まる）。ファイルから外し、画面（「日付を編集（カレンダー）」か 1 件ずつ）で変える
- ファイルの顧客コードが、選んでいる顧客と違うときは止まる
- 日付が変わったマーカーを参照するテンプレートは、未来の予定が作り直される
- 取り込みでは今日より前の日付も入れられる（最初の取り込みのため）

#### JSON ファイルの形

```json
{
  "client_code": "ABCD",
  "sheet_name": "年間計画",
  "period_start": "2026-04-01",
  "period_end": "2027-03-31",
  "markers": [
    {"marker": "本締", "description": "月次の本締め"},
    {"marker": "送付", "description": null}
  ],
  "events": [
    {"event_date": "2026-04-24", "marker": "本締"},
    {"event_date": "2026-04-27", "marker": "送付"}
  ]
}
```

| 項目 | 決まり |
|---|---|
| `client_code` | 登録済みで有効な顧客のコード（4 文字） |
| `sheet_name` | 1〜100 文字 |
| `period_start` / `period_end` | `YYYY-MM-DD`。終わりは始まりより後 |
| `markers` | 1〜100 件。`marker` は 1〜50 文字で、ファイルの中で重複しない。`description` は 200 文字まで（無くてもよい） |
| `events` | 0〜20,000 件。`event_date` は期間の中の日付、`marker` は `markers` にある名前 |

- 「動かさない日」（元の表の × など）は書きません。**ある日付だけ**を書きます。日付を消すのは「ファイルに合わせる」で、ファイルに無いことによって行います
- 文字コードは UTF-8。画面から取り込めるのは 4MB まで（20,000 件の日付で 1MB ほど）
- 見本: リポジトリの `mock_data/desensitized_mock_data.json`

#### API で取り込む場合

`POST /plans/sheets/import`（業務管理者でログインした Cookie が要る。本文は上の JSON そのまま）。新しく作ったときは 201、更新したときは 200。
「ファイルに合わせる」は `POST /plans/sheets/import?replace_events=true`。

**画面との違い:** API は期間を広げません。シートの期間はファイルの期間に置き換わり、「追加だけ」（`replace_events` なし）で今ある日付が新しい期間の外に出ると
400 で止まります。次の年の分を API で足すときは、`period_start` を今のシートの始まりのままにし、`period_end` だけを延ばしてください。

#### 画面でシートを作る・直す

ファイルが無くても、画面でシートを作り、マーカーと日付を入れられます（業務管理者）。

1. **シートを作る**: 「新しいシート」→ シートの名前と期間（既定は今年の 1/1〜12/31）→「作る」。空のシートができる
2. **シートの名前・期間を変える**: シートの「シートを編集」
   - 期間はいつでも延ばせる。ルールで日付を作るマーカーは、新しい期間まで日付を作る（翌年の分も同じシートに足せる）
   - 縮めるのは、新しい期間の外に日付が残らないときだけ（取り込んだ日付・人の日付・取り消した日付の記録・今日より前の日付が外に出ると止まり、その日付が表示される）。外に出るルールの未来の日付は消える
   - 同じ顧客に同じ名前のシートは作れない
3. **マーカーを足す**: 「マーカーを追加」→ 日付の作り方を選ぶ
   - **ルールで作る**: 毎月 27 日のように決まりで作れる基準日を、シートの期間全体に作る（休日の扱いと営業日カレンダーを選べる）
   - **日付を選んで作る**: 決まりの無い日付のマーカー。日付はここで選んでも、あとで「日付を編集（カレンダー）」で足してもよい
4. **マーカーを直す**: 行の「編集」で名前・説明（ルールのマーカーはルールも）を変える。「生成をやめる」でルールを止める
   - **名前を変えると、参照しているテンプレートも新しい名前になる**（日付も予定も変わらない）。テンプレートの「履歴」に「イベント記号」の変更として残る
   - 参照しているテンプレートに承認待ちの下書きがある、または承認待ちの下書きがこのマーカーを指しているときは、名前を変えられない（先に承認・差し戻し・取り下げ）
5. **マーカーを消す**: 行の「削除」。日付ごと消える。**テンプレート（削除したものも）や承認待ちの下書きが参照しているマーカーは消せない**（理由が日本語で表示される: 使っているテンプレートの名前と番号、削除したテンプレート、承認待ちの下書きの件数）
6. **日付をまとめて足す・消す**: マーカーの行を開き「日付を編集（カレンダー）」。シートの期間の年ごとに 12 か月のカレンダーが出る
   - 日をクリックすると「足す」（緑）、日付のある日は「消す」（取り消し線）。もう一度クリックで戻る。取り消した日の記録（点線）をクリックすると足し直す
   - 今日より前（実績）と期間の外は変えられない
   - 「保存する（+足す数 / −消す数）」で一度に保存する。参照しているテンプレートの予定は 1 回だけ作り直される。保存しないで閉じるときは確認が出る
   - 取り込み・ルールの日付を消すと「取消」として記録が残る（ルールの日付は「ルールに戻す」で戻せる）。人が足した日付は記録を残さずに消える
7. **日付を 1 件ずつ直す**: マーカーの行を開くと日付の一覧。日付ごとに「変更」（別の日へ動かす）・「ルールに戻す」・「削除」。出どころ（ルール / 人が変更 / 人が追加 / 取消 / 取り込み）が表示される

決まり（画面の編集）:

- 今日より前の日付は変えられない
- 日付を変えると、それを参照するテンプレートの未来の予定が作り直される

**API**

| 操作 | 呼び出し |
|---|---|
| シートを作る | `POST /plans/sheets` `{"client_code", "name", "period_start", "period_end"}` |
| 名前・期間を変える | `PATCH /plans/sheets/{id}` `{"name"?, "period_start"?, "period_end"?}`（送った項目だけ） |
| マーカーを足す | `POST /plans/sheets/{id}/markers` `{"marker", "description", "rule"}`（日付を選んで作るときは `rule` を省く） |
| マーカーの名前・説明・ルール | `PATCH /plans/sheets/{id}/markers/{marker}` `{"name"?, "description"?, "rule"?}` |
| マーカーを消す | `DELETE /plans/sheets/{id}/markers/{marker}`（参照があれば 409 `DELETE_FAILED_RECORD_IN_USE`） |
| 日付をまとめて足す・消す | `POST /plans/sheets/{id}/markers/{marker}/events/batch` `{"add": ["2026-12-01"], "remove": [日付の id]}` |

### 3.9 業務の依存関係

必要なロール: 業務管理者。画面: 設定 → 業務の依存関係（顧客を選ぶ）。同じ顧客の業務どうしだけ設定できます。

1. 「依存関係を追加」を押す
2. 上流（先に終わる業務）と下流（上流の完了を待つ業務）を選ぶ
3. 突き合わせ（下流のオーダーがどの上流のオーダーを待つか）を選ぶ

   | 突き合わせ | 待つ相手 |
   |---|---|
   | 同じシート日付 | 年間計画シートの同じ日付から作られた予定どうし |
   | 同じ日付 | ルール上の同じ日付の予定どうし（休日で動いても元の日付で突き合わせる） |
   | 直前の上流 | 下流の開始より前で最も近い上流のオーダー。何日前まで探すかを決める（既定 35 日） |

4. 種類を選ぶ: 「待つ」（上流が完了するまで下流を開始できない）/「参考」（表示するだけ）

変更はできません（削除して作り直す）。循環する設定（A → B → A）は保存できません。

待っている下流のオーダーには日次ダッシュボードで「待ち」が付き、「開始」が出ません。上流を待たずに始めるときは
リリース担当か業務管理者が理由を入れて承認します（3.11）。上流が取消・保留になっても、下流は自動では開始できるようになりません。

**API**: `GET /biz/clients/{client_code}/dependencies`、
`POST /biz/{下流の biz_id}/dependencies` `{"upstream_biz_id": 1, "match_rule": "same_occurrence_date", "kind": "hard"}`
（`match_rule`: `same_sheet_event` / `same_occurrence_date` / `latest_before`（`lookback_days` が必須）、`kind`: `hard` / `informational`）、
`DELETE /biz/dependencies/{id}`。

### 3.10 カレンダー（予定を見る・動かす）

画面: ナビ「カレンダー」。顧客と月を選ぶと、その月の予定が日ごとに並びます。分類や予定名で表示を絞れます。
日をダブルクリックすると、その日の日次ダッシュボードが開きます。

予定を動かす操作に必要なロール: リリース担当 または 業務管理者（ほかの職員は見るだけ）。

| 操作 | やり方 | 結果 |
|---|---|---|
| 日時を変える | 予定の「変更」→ 新しい日時を入れて「変更する」 | 予定が動き、オーダーも追従する |
| 取り消す | 予定の「取消」→「取り消す」 | 予定が消え、オーダーは取消になる |
| ルールどおりに戻す | 変更した予定の「元に戻す」 | ルールの日時に戻る |
| 臨時の予定を足す | 「臨時の予定」→ テンプレートと日時を選んで「追加する」 | その 1 回だけの予定とオーダーができる |
| 取り消した予定を戻す | 「取消済みの予定」の一覧 →「元に戻す」 | 予定が戻り、新しいオーダーができる（取消になったオーダーは履歴として残る） |

きまり:

- **作業中のオーダーの予定は、人が変更・取消できない**（エラーになる）。オーダー側で保留・取消をする
- 人が変更・取消した予定は、ルールや休日を変えても自動では作り直されない
- リリース済のオーダーの予定を動かして、ステップの条件（月・週の最初）の当てはまり方が変わると「矛盾」が付く

**API**: `GET /plans/clients/{code}/calendar?month=2026-11`、
`POST /plans/instances/{id}/override` `{"scheduled_start": "2026-11-20T09:00:00+09:00", "note": "..."}`、
`POST /plans/instances/{id}/cancel`、`POST /plans/instances/{id}/revert`、
`POST /plans/templates/{id}/instances` `{"scheduled_start": "..."}`（臨時）、
`GET /plans/clients/{code}/cancelled?start=...&end=...`、`POST /plans/instances/{id}/restore`。

### 3.11 日次ダッシュボードとオーダーの操作

画面: ナビ「日次ダッシュボード」。日付を選ぶと、全顧客のその日に始まる予定が 顧客 → 業務 の順に並びます。

- 行に出るもの: 時刻、予定名、オーダーの状態、ステップの進み（例 `2/3`）、矛盾 / 待ち / まもなく / 遅れ、締切（予定の終了と違うとき）
- 行を押すと右にオーダーの詳細が開く: 状態、予定、SOP の版、締切、ステップ、依存関係、記録（誰がいつ何をしたか）
- 歯車の印から、その予定のテンプレートの設定へ移れる
- 過去の日付では、取り消された予定も理由付きで表示される

**オーダーの操作**（詳細の中のボタン。自分のロールと状態で使えるものだけ出ます）

| 操作 | 必要なロール | できる状態 | 条件・理由の入力 | API（`POST /ope/orders/{id}/…`） |
|---|---|---|---|---|
| リリース | リリース担当・業務管理者 | 未リリース | 矛盾がないこと。自動の業務でも手で出せる | `release` |
| 開始 | 作業者 | リリース済 | 予定日（日本時間）以降。矛盾がないこと。待つ上流が完了していること | `start` |
| 予定日前の開始を承認 | リリース担当 | 未リリース・リリース済 | 予定日より前に始めたいとき。承認後に作業者が開始する | `approve-early-start` |
| 依存関係を待たずに開始を承認 | リリース担当・業務管理者 | 未リリース・リリース済 | **理由が必須**。承認後に作業者が開始する（予定日のきまりは別に残る） | `approve-dependency-override` |
| 保留 | 作業者・リリース担当・業務管理者 | 未リリース・リリース済・作業中 | **理由が必須**。保留中はステップを操作できない | `hold` |
| 再開 | 同上 | 保留中 | 止める前の状態に戻る | `resume` |
| 完了 / 受領 | 作業者 | 作業中（顧客側の出来事はリリース済からも） | **ステップのないオーダーだけ**。「信号で自動」の業務を手で完了にするときは理由が必須 | `finish` |
| 取消 | リリース担当・業務管理者 | 完了・取消以外 | **理由が必須**。カレンダーの予定も取り消される | `cancel` |
| 矛盾を解決 | リリース担当・業務管理者 | 矛盾が付いているとき | 下の 3 つから選ぶ | `resolve-conflict` |
| SOP バージョンを指定 / 解除 | リリース担当・業務管理者 | 未リリース | その業務の承認済みの版から選ぶ | `pin`、`unpin` |

矛盾の解決の選択肢:

| 選択肢 | 結果 |
|---|---|
| 予定の新しい日時を採用 | オーダーを今の予定に合わせる。予定がなくなっていれば取消。開始前でステップの当てはまりが変わっていれば、ステップを作り直す |
| このまま続ける | 印だけ消す。ステップは今のまま |
| オーダーを取り消す | 理由が必須 |

ステップのあるオーダーは「完了」のボタンが出ません。最後のステップが承認されると自動で完了になります。
矛盾が付いている間は、最後のステップが承認されても作業中のままで、矛盾を解決すると完了になります。

**API**: 一覧 `GET /ops/daily?date=2026-11-10`、詳細 `GET /ope/orders/{id}`。
操作の本文は、理由が必須のもの `{"reason": "..."}`、任意のメモ `{"comment": "..."}`、
矛盾の解決 `{"action": "accept_plan"}`（`accept_plan` / `keep` / `cancel`）、版の指定 `{"sop_version_id": 3, "reason": "..."}`。

### 3.12 ステップの提出・承認・差し戻し

場所: オーダーの詳細の「ステップ」。オーダーが**作業中**のときだけ操作できます。

ステップの状態: 待機（まだ開いていない）→ 未提出 → 確認待ち → 承認済。

1. 作業者がオーダーを「開始」すると、最初のステップが「未提出」になる
2. 作業者が作業を終えて「提出」を押す（メモは任意）→「確認待ち」
3. 確認者が内容を確かめて「承認」を押す →「承認済」。直しが要るときは「差し戻し」（**理由が必須**）→ そのステップだけ「未提出」に戻る
4. 次のステップは、前のステップの**提出**で開く。前のステップに「承認で次へ」が付いていれば**承認**で開く
5. すべてのステップが承認されると、オーダーは自動で「完了」になる

きまり:

- **自分が提出したステップは、自分では承認・差し戻しできない**（作業者と確認者の両方のロールを持っていても）。別の人が提出し直せば、最初の提出者は承認できる
- 差し戻しても、先のステップの状態は変わらない
- リリースの前は、ステップは「予定」として表示されるだけ（条件に当てはまるものの見込み）

**API**: `POST /ope/steps/{step_id}/submit`、`POST /ope/steps/{step_id}/approve`、
`POST /ope/steps/{step_id}/reject` `{"reason": "..."}`。ステップの番号（`step_id`）は `GET /ope/orders/{id}` の `steps` にあります。

### 3.13 締切・遅れの確認

場所: 日次ダッシュボードのタブ「締切・遅れ」。タブに件数が出ます（遅れがあれば赤、まもなくだけなら金色）。

- 日付に関係なく、完了・取消になっていないオーダーのうち「まもなく」と「遅れ」のものが、締切の早い順に並ぶ
- 行を押すとオーダーの詳細が開く
- 締切はテンプレートで決めたきまり（3.7）から、オーダーに記録される。リリースの後にテンプレートを変えても変わらない。
  予定が動いたときは、オーダーが持っているきまりで計算し直される

**API**: `GET /ops/attention?limit=100`。

### 3.14 顧客側の出来事と信号

ファイルの受領のような「顧客側で起きること」を、ステップのない業務として扱います（3.4 で 実行のしかた = 顧客側の出来事）。

**手で受領を記録する（完了のしかた = 作業者が受領を記録する）**

1. オーダーがリリース済になったら、作業者が顧客からの受領を確かめる
2. オーダーの詳細で「受領」を押す → 完了。開始の操作は要らない

**信号で自動的に完了する（完了のしかた = 信号で自動的に完了する）**

外部の仕組みが `POST /api/ope/signals` を呼ぶと、当てはまるオーダーが自動で完了になります。

- 照合: 信号の種類（業務の設定と同じ値）+ 顧客コード + キー（オーダーのルール上の日付 `YYYY-MM-DD`）
- 完了にできるのは、リリース済か作業中のオーダーだけ

| 結果 | 意味 |
|---|---|
| 完了にした | 当てはまるオーダーが 1 件あり、完了にした |
| 重複（すでに完了） | そのオーダーはもう完了している（同じ信号がもう一度来た） |
| 照合できない | 当てはまるオーダーがない、まだ未リリース、保留中、矛盾がある、キーが日付でない、など |
| 候補が複数 | 当てはまるオーダーが 2 件以上ある |

信号はどの結果でも記録に残ります。「照合できない」と「候補が複数」は人の対応が必要です。

**対応する**（作業者・リリース担当・業務管理者）: 日次ダッシュボードのタブ「信号」→ 行の「対応」→
メモ（必須）と、完了にするオーダーの番号（任意）を入れる。対応は 1 回だけで、あとから変えられません。

信号が来ないとき: 作業者がオーダーの詳細で「受領」を押し、理由を入れて完了にできます。

**API**

| 操作 | 呼び出し |
|---|---|
| 信号を送る | `POST /ope/signals`（**API キー**）`{"type": "data_received", "client_code": "ABCD", "key": "2026-11-10", "received_at": "2026-11-10T08:55:00+09:00"}` |
| 一覧 | `GET /ope/signals?scope=open`（`open` = 対応待ち / `all`） |
| 対応 | `POST /ope/signals/{id}/handle` `{"note": "...", "order_id": 123}` |

### 3.15 SLA レポート

画面: ナビ「SLA」。有効な職員なら誰でも見られます。

1. 月の範囲（既定は直近 12 か月、最長 36 か月）と顧客を選ぶ
2. 顧客 × 月（**締切のある月**、日本時間）ごとに次が出る

   | 列 | 意味 |
   |---|---|
   | 完了 | その月が締切で、完了したオーダーの数 |
   | 遅れ | そのうち、締切より後に完了した数 |
   | 期限内率 | （完了 − 遅れ）÷ 完了 |
   | 平均遅れ（分） | 遅れたオーダーだけの平均 |
   | 未完了の遅れ | 締切を過ぎてまだ完了していない数（上の数字には入らない） |

3. 「CSV を出力」で、表示している行をそのまま保存する（Excel で開ける）

取消になったオーダーは数えません。

**API**: `GET /ops/sla?from=2026-01&to=2026-11&client_code=ABCD`。

### 3.16 記録された出来事と通知（遅れ・まもなく・通知の記録）

画面: ナビ「出来事・通知」のタブ「出来事」。ログインした職員なら誰でも見られます（担当顧客が限られた職員には、その顧客の分だけ）。読み取りのみです。

システムは毎分、締切を見張り、次の 2 つを **出来事** として記録します。通知（メール）は、この出来事に当てはまるルール（3.18）があるときに送ります
（通知はこの記録をもとに、後の段階で送ります）。この画面は、正しいオーダーが正しい時刻に記録されたかを確かめるためのものです。

| 種類 | 記録されるとき | 起きた日時 |
|---|---|---|
| 遅れ（`OrderLate`） | 完了・取消になっていないオーダーの締切が過ぎた | 締切 |
| まもなく（`OrderDueSoon`） | 「まもなく」の時刻（テンプレートの「締切の何分前から」）を過ぎて、締切はまだ | 「まもなく」の時刻 |

きまり:

- 1 件のオーダーにつき、**締切ごとに 1 回**だけ記録する。予定が動いて締切が変われば、新しい締切でもう一度記録される
- 見つけたときにもう締切を過ぎていれば「遅れ」だけ（締切の後に「まもなく」は記録しない）
- **過ぎてから 24 時間以内**のものだけ記録する。システムが止まっていた間の分は、動き出したときに記録される（列「記録」に「N 分後」）。
  24 時間より前から遅れたままのオーダーは記録しない（日次ダッシュボードの「締切・遅れ」には出る）
- テンプレートや業務を削除しても、まだ開いているオーダーは見張り続ける
- 記録は後から変えられない。中身は **記録した時点の写し**（顧客名・業務名・予定名・予定日・締切・オーダーの状態）なので、
  後でオーダーが変わっても、記録は当時のまま

使い方:

1. 種類・顧客・オーダー ID・期間（日本時間の日付。両端を含む）で絞り込む。絞り込みは URL に残るので、そのまま共有できる
2. 新しい順に 200 件まで出る。もっとあるときは案内が出るので、期間などで絞る
3. 行の左の「+」で開くと、記録の中身（JSON）と、重複を防ぐキー、**その出来事から作った通知**（状態・ルール・宛先ごとの結果）が
   見られる。「「通知」タブで詳しく見る」で、その出来事の通知だけをタブ「通知」に出す
4. 列「通知の処理」: 通知の仕組みが毎分その出来事を読むと「処理済み」になる（当てはまるルールがなければ、通知は作られない）。
   読めなかったときは「失敗 N 回」（次の回にもう一度。5 回であきらめる）
5. 「再読み込み」で最新にする（自動では読み直さない）

種類には、宛先の **テスト送信**（3.18）も出ます（オーダーの列は「—」、業務の列に宛先の名前）。

**タブ「通知」（通知の記録）**: 作った通知を新しい順に並べます。出来事 → 通知 → 宛先ごとの配信 → 1 回ごとの送信、をたどれます。

1. 状態（届いた / 一部に届かなかった / 届かなかった / 送信中・待ち / 知らせなかった）・種類（アラーム / テスト送信）・顧客・期間で絞り込む
2. 行ごとに、作った日時・出来事の種類・顧客・件名・ルール（テスト送信は「テスト送信」）・状態・宛先ごとの結果
3. 行を開くと、宛先ごとに **何回目に・いつ・どのアドレスへ送り・どうなったか・相手のサーバーの返事**、と本文。
   宛先のアドレスを途中で直したときは「送った後にアドレスが直されています」と出て、前の回のアドレスも残っている
4. 「知らせなかった」通知には理由が出る（重複の期間内 / 知らせない時間帯 / 使える宛先がない / 文面がない）

**API**: `GET /events/?event_type=OrderLate&client_code=ABCD&order_id=123&from=2026-11-12T00:00&to=2026-11-13T00:00&limit=100`
（from 以上・to 未満。タイムゾーンのない日時は日本時間。API キーでは呼べない）。
通知の記録: `GET /notifications/log?event_id=123&status=failed&kind=alarm`、1 件: `GET /notifications/log/{id}`。

### 3.17 届かなかったアラーム（通知の失敗）

場所: 日次ダッシュボード。有効な職員なら誰でも見られます（担当顧客が限られた職員には、その顧客の分だけ）。

アラーム（遅れ・まもなくの通知）は、届かなければ 1・5・15・60 分後に送り直し、5 回目でもだめなら **届かなかった** になります。
宛先が存在しないなど、送り直しても無駄なときはすぐに。届かなかったアラームは、だれかが **「確認した」** を押すまで消えません。

| 画面のどこ | 何が出るか |
|---|---|
| ナビの「日次ダッシュボード」 | まだ確認されていない、届かなかったアラームの件数（赤）。どの画面からも見える |
| ダッシュボードの上の赤い帯 | 「届かなかったアラームが N 件あります。確認してください。」どのタブ・どの日付でも出る。「確認する」でタブ「通知の失敗」へ |
| ダッシュボードの上の黄色の行 | 「メールの送信を再試行中: N 件（最後の失敗 時刻: 理由）」。いま送り直している配信があるとき。メールサーバーの不調の早い知らせ（約 80 分待たずに気づける） |
| タブ「通知の失敗」 | 届かなかったアラームの一覧（まだ確認していないもの → 確認済み（直近 7 日・薄く）） |

一覧の見方と対応:

1. 行ごとに、アラームを作った日時・種類（遅れ / まもなく）・顧客・件名・状態（届かなかった / 一部に届かなかった）・ルール、
   **宛先ごとの結果**（届いた / 届かなかった（試した回数））と **相手のサーバーの返事**（例: `550 5.1.1 no such user` = 宛先がない）
2. 行を押すと、そのオーダーの詳細が開く（いまの状態を確かめる）
3. 必要な人に電話などで伝えたら **「確認した」** を押す。赤い帯・件数から消え、行は「確認済み」に移って「確認: 名前 日時」が出る
   （7 日たつと一覧からも消える）。押せるのは作業者・確認者・リリース担当・業務管理者（閲覧者・監査担当・システム管理者は見るだけ）
4. 同じ宛先で何度も届かないときは、宛先のアドレスやメールサーバーの設定を見直す（サーバーの設定: `deploy/README.md` の「通知のメール」）

確認していないものは古くても残ります（気づかないまま消えることはありません）。

**API**: `GET /notifications/failures`、`POST /notifications/{id}/acknowledge-failure`（届いた・再試行中の通知は 400）。

### 3.18 通知の設定（ルール・宛先・テスト送信）

画面: ナビ「設定」→「通知の設定」。見るのは有効な職員なら誰でも。変えるのは **業務管理者** だけです。
担当顧客が限られた業務管理者は、自分の顧客のルール・宛先だけを作り・変えられます（全顧客のものは「変更できません」と出ます。
全顧客の宛先は、自分のルールで使えて、テスト送信もできます）。

**宛先**（タブ「宛先」）: 知らせる先のメールアドレス。

1. 「宛先を作る」: 名前・メールアドレス・顧客（全顧客 = どの顧客のルールでも使える）・持ち主のチーム・有効
2. **「テスト送信」**: 本物のアラームと同じ道で 1 通送る。すぐ「送信待ち（1 分以内）」になり、1 分ほどで「届いた」か
   「届かなかった」（相手のサーバーの返事つき）に変わる（画面が自分で読み直す）。テスト送信は送り直さない。
   届かなかったテストは、日次ダッシュボードの「届かなかったアラーム」には数えない
3. 「直す」: アドレスを直すと、**まだ送り直している配信も新しいアドレスへ送る**（打ち間違いを直せば、約 80 分のうちなら届く）。
   どの回にどのアドレスへ送ったかは、通知の記録に残る（3.16）
4. 「削除」: ルールが使っている宛先は削除できない（ボタンにそのルールの名前が出る）。先にルールから外す。削除は「削除したものも表示」から元に戻せる
5. 無効にすると、その宛先には送らない（ルールからは外れない）

**ルール**（タブ「ルール」）: どの出来事を・どの顧客（業務）について・どの宛先に知らせるか。

| 項目 | 意味 |
|---|---|
| 知らせる出来事 | 遅れ / まもなく（両方も選べる） |
| 顧客・業務 | 全顧客 / 顧客 / その顧客の業務。全顧客のルールで顧客の宛先を選ぶと、その顧客の出来事のときだけ届く |
| 宛先 | 1 つ以上。全顧客の宛先と、ルールの顧客の宛先から選ぶ |
| 文面 | 今は「オーダーの遅れ・まもなく」だけ |
| 重複の期間（分） | 同じオーダー・同じ種類の通知を、この分数のうちは 2 回出さない（締切が何度も動いたとき）。「まもなく」が「遅れ」を消すことはない |
| 知らせない時間帯 | 例: 22:00〜07:00（日をまたいでよい）。その時間帯の出来事は「終わってから知らせる」か「知らせない」 |
| 有効 | 無効のルールでは知らせない |

- 変更は **保存した後に起きる出来事から** 効く。もう作った通知は、そのときのルールのまま
- 「最終更新」に、最後に変えた人と日時が出る
- 削除は元に戻せる（宛先が削除されていると、先に宛先を元に戻すよう案内が出る）

**API**: `GET/POST /notifications/rules`、`PUT/DELETE /notifications/rules/{id}`、`POST …/restore`、
`GET/POST /notifications/destinations`、`PUT/DELETE /notifications/destinations/{id}`、`POST …/restore`、`POST …/{id}/test`（202）。

### 3.19 ワーカーの状態（並行稼働の承認の記録）

画面: ナビ「ワーカーの状態」。ログインした職員なら誰でも見られます（参照のみ）。1 分ごとに自分で読み直します。

**ワーカー** は、毎分の自動処理（自動リリース・予定の生成・締切の監視・通知の振り分けと配信）を回すプログラムです。
1 回り終えるたびに **心拍** を残し、仕事が失敗すると、その **エラー** を記録して次の仕事に進みます。
並行稼働の承認の条件の 1 つ「ワーカーに処理されないエラー・落ちることが無かった」は、この画面で確かめます。

| 画面のどこ | 何が出るか |
|---|---|
| ナビ「ワーカーの状態」の赤い点 | ワーカーが動いていない（最後の心拍が 5 分より古い・止まった・一度も動いていない）。どの画面からも見える |
| 日次ダッシュボードの上の赤い帯 | 「ワーカーが N 分間動いていません（最後の動作 時刻）。自動リリース・締切の監視・通知の送信が止まっています。」「ワーカーの状態へ」でこの画面へ。ワーカーが戻れば次の読み直し（1 分以内）で消える（「確認した」は要らない） |
| 上の「いま」 | 動いている / 止まっている（心拍が途絶えた・停止した）/ まだ一度も動いていない、最後の心拍、この実行の起動 |
| 判定（緑 / 赤） | 期間（既定は今日までの 14 日、最大 62 日）に **承認に数える問題** があるか。回り・稼働率・最長の間隔・起動の回数 |
| 1 日ごとの表 | 日本時間の日ごと（新しい日が上）: 判定・問題・回り（ふつう 1 日 1,440）・稼働率・最長の間隔・最も遅い回り・エラー（仕事ごと）・途切れ・止まり方・起動・処理済みの問題。行を開くと途切れ（いつからいつまで、今も続いているか）と止まり方の中身 |
| 受け止めたエラー | 日時・仕事・種類・内容・マシン。行を開くとトレースバック（開発者に渡す） |

**承認に数える問題** = 次の合計です。

1. **エラー**: ワーカーが仕事の失敗を受け止めた回数（データベースが一時的に止まった・設定の誤りなど）
2. **途切れ**: 心拍と心拍の間が 5 分を超えたところ（再起動をまたいでも数える）。**予定した停止（新しい版への入れ替えなど）も途切れに出ます。**
   理由を承認の記録に書いてください（システムはどの停止が予定どおりかを判断しません）
3. **きれいに止まらなかった実行**: 落ちた（想定外のエラー）か、止まった印のないまま心拍が途絶えた（強制終了・ハング）

**処理済みの問題**（届かなかった通知・5 回で諦めた出来事）は数えません。それぞれ 3.17・3.16 の画面で扱います
（宛先の打ち間違いでワーカーの承認が落ちないように）。担当顧客が限られた職員には、その顧客の分だけが出ます。

並行稼働の終わりに: 期間を 14 日に合わせて **「CSV を出力」**（1 日 1 行と合計の行。Excel でそのまま開ける）し、
新旧 mfa.txt の照合のまとめ（`adapters/mfa/README.md`）と一緒に承認の記録に付けます。
並行稼働の準備・毎日の確認・終わりの手順と承認の記録の表は `deploy/GO-LIVE.md` の「I. 並行稼働（14 日間）」にあります。

**API**: `GET /worker-health/summary?from=&to=`、`GET /worker-health/errors?from=&to=&job=`（ログインが要る）。

## 4. API の呼び方

### 4.1 ログインして呼ぶ（curl の例）

```sh
BASE=http://<サーバー>/api

# ログイン（Cookie を cookie.txt に保存する）
curl -s -c cookie.txt -H "Content-Type: application/json" \
     -d '{"login_id": "admin", "password": "<パスワード>"}' $BASE/auth/login

# 以後は Cookie を付けて呼ぶ
curl -s -b cookie.txt $BASE/staff/me
curl -s -b cookie.txt "$BASE/ops/daily?date=2026-11-10"

# 本文のある操作
curl -s -b cookie.txt -H "Content-Type: application/json" \
     -d '{"reason": "顧客の依頼で延期"}' $BASE/ope/orders/123/hold

# ログアウト
curl -s -b cookie.txt -X POST $BASE/auth/logout
```

### 4.2 API キーで呼ぶ（信号の送信・読み取り）

**信号を送る**（「信号の送信」のキー）:

```sh
curl -s -H "Authorization: Bearer ops_xxxxxxxx" -H "Content-Type: application/json" \
     -d '{"type": "data_received", "client_code": "ABCD", "key": "2026-11-10", "received_at": "2026-11-10T08:55:00+09:00"}' \
     http://<サーバー>/api/ope/signals
```

**まもなく・遅れのオーダーと日次の状況を読む**（「システム連携（読み取り）」のキー。mfa のアダプターなど）:

```sh
curl -s -H "Authorization: Bearer ops_xxxxxxxx" "http://<サーバー>/api/ops/attention?limit=200"
curl -s -H "Authorization: Bearer ops_xxxxxxxx" "http://<サーバー>/api/ops/schedule-feed?days=30"   # これから始める作業の時刻表（mfa のアダプター）
curl -s -H "Authorization: Bearer ops_xxxxxxxx" "http://<サーバー>/api/ops/daily"
curl -s -H "Authorization: Bearer ops_xxxxxxxx" "http://<サーバー>/api/staff/me"   # キーが使えるかの確認
```

キーで呼べるのは、そのアカウントのロールに許された呼び出しだけです。ほかの API に付けても 401 になります。
キーにログインの期限はありません（取り消すまで使える）。担当顧客を決めたアカウントのキーは、その顧客の分だけを返します。

**これから始める作業の時刻表**（`GET /api/ops/schedule-feed?days=30`。1〜31 日。`from=` で始まりを指定、タイムゾーンなしは日本時間）:
予定の **開始** の順に、人が動く作業だけを返します。

- 分類（予定テンプレート設定の「分類」）が **不定期・スペシャル** のもの（既定。`categories=regular` などで変えられる）。
  分類を決めていないテンプレートは定例として扱う。臨時に追加した予定は、テンプレートの分類によらずスペシャル
- まだ始めていないオーダー（**未リリース・リリース済**）だけ。取消・保留・作業中・完了は出ない
- テンプレートの **「開始時刻に知らせる」がオン** のものだけ（外からの合図を待つ作業はオフにして出さない。臨時の追加もテンプレートに従う）
- 各行に顧客・業務・予定名・予定日・開始・終了・締切・状態と、行を突き合わせるための `key`

### 4.3 エラーの形

エラーは次の形で返ります（メッセージは英語。画面は主なものを日本語にして出します）。

```json
{"status_code": 403, "error_code": "FORBIDDEN", "message": "..."}
```

一部のエラーには、理由を形の決まった情報で返す `details` が付きます（画面はこれで日本語の文を作ります。形は各 API の
OpenAPI に書いてあります）。今は、使われているマーカーの削除（`DELETE /plans/sheets/{id}/markers/{marker}` の 409）だけです:

```json
{"status_code": 409, "error_code": "DELETE_FAILED_RECORD_IN_USE", "message": "Marker '受領' is in use: ...",
 "details": {"marker": "受領", "templates": [{"id": 12, "name": "毎日"}], "deleted_templates": [], "draft_change_ids": []}}
```

| 状態コード | 主な `error_code` | 意味 |
|---|---|---|
| 400 | `BAD_REQUEST` | 今の状態ではできない操作、きまりに合わない値（メッセージに理由） |
| 401 | `UNAUTHORIZED`、`INVALID_CREDENTIALS` | ログインしていない・切れた / ログインID かパスワードが違う |
| 403 | `FORBIDDEN` | ロールが足りない |
| 403 | `STAFF_NOT_ACTIVE` | アカウントが利用開始前・停止中 |
| 403 | `PASSWORD_CHANGE_REQUIRED` | 仮パスワードのまま（`/staff/me`、`/auth/password`、`/auth/logout` だけ使える） |
| 403 | `ACCOUNT_LOCKED` | ログインの失敗が続いてロック中 |
| 403 | `FOUR_EYES` | 自分が提出したステップを承認・差し戻ししようとした |
| 403 | `ALL_CLIENTS_REQUIRED` | 担当顧客が限られた職員が、全顧客に共通の設定（顧客・休日カレンダーの変更・職員・API キー）を使おうとした |
| 404 | `NOT_FOUND` | 対象がない。担当顧客が限られた職員には、ほかの顧客のものも同じく 404（画面は「見つかりません」） |
| 409 | `RECORD_ALREADY_EXISTS`、`ORDER_IN_PROGRESS`、`DELETE_FAILED_RECORD_IN_USE` | 重複 / 作業中のオーダーの予定を動かそうとした / 使用中で削除できない（テンプレートが参照するシートのマーカーなど） |
| 409 | `TEMPLATE_DRAFT_PENDING` | 承認待ちの下書きがあるテンプレートを変更・削除しようとした、2 つ目の下書きを書こうとした、または承認待ちの下書きが関わるシートのマーカーの名前を変えようとした |
| 409 | `TEMPLATE_CHANGE_DECIDED` | もう承認・差し戻し・取り下げが済んだ下書きを直す・決めようとした |
| 409 | `TEMPLATE_CHANGED_MEANWHILE` | 下書きを確かめている間にテンプレートが変わった（もう一度保存する） |
| 409 | `SOP_DRAFT_SUBMITTED` | 承認を依頼中の SOP の草稿を直す・削除する・もう一度依頼しようとした |
| 409 | `SOP_DRAFT_NOT_SUBMITTED` | 依頼していない SOP の草稿を取り下げる・差し戻そうとした |
| 422 | （FastAPI の形式） | 本文の項目が足りない・型が違う |

自動の処理を確かめるとき:

- 業務のリリースの方法を「自動」、時刻を数分後にする → その時刻から 1 分ほどで「リリース済」になる（記録の操作者はシステム）
- 「信号で自動的に完了する」業務を作り、API キーで信号を送る（4.2）→ リリース済のオーダーが完了になる。
  未リリースのうちに送ると「照合できない」としてタブ「信号」に出る

開始の知らせ（29〜31）を確かめるとき:

- 開始の知らせは **通知（メール）ではありません**。「通知の設定」のルールに種類が無く（遅れ・まもなくだけ）、「出来事・通知」の
  画面にも出ません。新しいシステムは「いつ始めるか」の時刻表（`GET /api/ops/schedule-feed`）を出すだけで、アダプターがそれを
  mfa の設定ファイル（mfa.txt）の `Msg` の行にし、**鳴らすのは mfa** です（2026-11-16 の決定: 開始の知らせは mfa に任せる）
- だから確かめるのは、時刻表（29・30）と、アダプターが書く行（31）です。時刻表はログインした職員なら誰でもブラウザで開けます
  （読み取りだけ。担当顧客が決まった職員には、その顧客の分だけ）
- 実際に音が鳴るかは、並行稼働（[GO-LIVE.md](../deploy/GO-LIVE.md) の I.）では確かめません: その間、mfa は旧来の mfa.txt を
  読み続け、新旧の時刻が 3 分以内で合うことだけを照合します。新しいファイルで mfa が鳴ることは、mfa を切り替える前に
  別に確かめます（試しの PC の mfa に、アダプターの出力のフォルダーを読ませる）

## 6. MVP の制限

| 項目 | 今の状態 |
|---|---|
| 通信 | 社内ネットワークの http だけ（HTTPS・社外からの利用はなし） |
| 通知 | メールだけ（チャットへの通知はない）。ルール・宛先は画面で設定する（3.18）。文面は「オーダーの遅れ・まもなく」の 1 種類。ルール・宛先の変更前後の履歴はない（最後に変えた人と日時だけ）。届かなかったアラームは日次ダッシュボードに出る（3.17） |
| 顧客ごとの閲覧制限 | 担当顧客で決める（1.4）。社外の人（顧客の担当者）のアカウントは想定していない（履歴に職員の名前が出るなど、社外向けの確認はまだ） |
| 営業日カレンダーの作成・週末の変更 | 画面なし（サーバーのスクリプトか API） |
| 年間計画シートの元の表（Excel など）の読み取り | システムは読まない。利用者の側で JSON ファイルに変換して取り込むか、画面で入力する（3.8） |
| 年間計画シートの削除 | 画面も API もない（マーカーと日付は画面で消せる） |
| マーカーの削除 | 一度でもテンプレートが参照したマーカーは消せない（削除したテンプレートも、元に戻せるため数える）。名前は変えられる |
| 削除したテンプレートの復元 | 画面なし（API `POST /plans/templates/{id}/restore` はある） |
| 依存関係の変更 | 削除して作り直す |
| SOP の承認 | 業務管理者 1 人でできる（自分の草稿も承認できる。その場合は履歴に残る）。リリース担当の草稿の通知はなく、件数の印と承認待ちの画面で確かめる |
| SOP の履歴 | 2026-11-11 以降の操作から。ステップの 1 つずつの編集は記録しない（最後に直した人と日時だけ）。草稿を削除すると、その履歴も消える |
| テンプレートの下書き | 承認されるとすぐに反映される（日を予約する仕組みはない）。下書きの通知はなく、業務管理者は件数の印と承認待ちの画面で確かめる |
