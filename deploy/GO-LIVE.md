# 本番の使い始め（チェックリスト）

サーバーを立てたあと、実際に使い始めるまでに 1 回だけ行う作業です。上から順に進め、終わったら `[x]` にします。
最初は **1 つの顧客だけ**（パイロット）で始め、数日使って問題がなければ残りの顧客を足します（H）。
サーバーの立て方・更新・ログ・バックアップの基本は [README.md](README.md) を見てください。

- コマンドはすべて `/srv/ops/current/deploy` で実行します（`docker compose …`。docker グループに入っていなければ先頭に `sudo`）。
- `-U ops -d ops` は `.env` の `POSTGRES_USER` / `POSTGRES_DB` です。違う値にしたときは読み替えてください。
- 画面の操作には **業務管理者**（設定の変更）や **システム管理者**（職員の管理）のロールが要ります。

## A. 事前の確認（データを入れる前）

Gitea とパイプライン（[gitea-runbook.md](gitea-runbook.md) と README.md の 3.4）:

- [ ] `http://<サーバー>:3000/` にログインでき、自分で登録する画面が無い
- [ ] リポジトリの「設定 → Actions → ランナー」に `ops-server` が **アイドル**
- [ ] 「設定 → Actions → 変数」の `DEPLOY_USERS` に、デプロイしてよい人だけが入っている
- [ ] main の push で `backend` と `frontend` が緑
- [ ] `DEPLOY_USERS` に**無い**人が「Run workflow」を押すと、`gate` が赤で止まり、`deploy` は動かない
- [ ] `DEPLOY_USERS` の人が「Run workflow」を押すと全部緑になり、`/srv/ops/deploys.log` の最後の行が `ok`
- [ ] 次の日、`/srv/gitea/data/backups/` に `gitea-YYYYMMDD.zip` がある

アプリ:

- [ ] `docker compose ps` で `db` / `app` / `worker` / `web` / `backup` が動いていて、`app` が `healthy`
- [ ] ブラウザで `http://<サーバー>/` を開くとログイン画面が出る
- [ ] `docker compose logs worker` に `Worker started (automatic release, …)` が出ている
- [ ] `docker compose logs backup` に `backup: daily at 01:00, keeping 14 days in /backups` が出ている
- [ ] **復元の練習**（本番のデータには触らず、別のデータベースへ戻して比べる）:

  ```sh
  docker compose exec backup sh /backup.sh once        # 今すぐバックアップ（ファイル名がログに出る）
  ls /srv/ops/backups/                                 # .env の BACKUP_DIR を変えたときはそのフォルダー
  docker compose exec db createdb -U ops ops_restore_check
  docker compose exec -T db pg_restore --no-owner -U ops -d ops_restore_check < /srv/ops/backups/ops_YYYYMMDD_HHMMSS.dump
  docker compose exec -T db psql -X -A -t -U ops -d ops < restore-check.sql
  docker compose exec -T db psql -X -A -t -U ops -d ops_restore_check < restore-check.sql
  docker compose exec db dropdb -U ops ops_restore_check
  ```

  - [ ] `pg_restore` がエラーを出さずに終わる
  - [ ] 2 つの `psql` の結果（alembic の版と各テーブルの件数）が同じ
  - [ ] 最後に `ops_restore_check` を消した

## C. パイロットの顧客を 1 つ入れる

### C-0. テスト環境で作ったマスタデータをまとめて入れる（シードデータ）

テスト環境で顧客・業務・SOP・シート・テンプレートを作り込んであるときは、画面で 1 つずつ入れる代わりに、
`scripts/export_seed.py` で書き出して `scripts/import_seed.py` で入れます（画面と同じ API で作るので、確かめも同じ）。
画面で入れるときは C-0 を飛ばして下の手順へ。

- 持っていくもの: 営業日カレンダーと休日・顧客（有効 / 無効）・業務と設定・業務の依存関係・SOP（現行と予定の版と手順）・
  年間計画シート（マーカー・今の日付・生成のルール）・予定テンプレート
- 持っていかないもの: オーダー・予定（カレンダーでの変更を含む）・シグナル・出来事・通知・職員・通知の設定・API キー・
  SOP とテンプレートの履歴・下書き・削除したもの。**職員と通知の設定は D と並行稼働（I）の手順で入れます**
- **使い始めの前日に行います**: テンプレートを作ると本番でもすぐに予定とオーダーができます。現行の SOP は
  `--effective-date`（使い始めの日。明日以降）から効きます
- 前提: A・B が終わっている（B の `admin` で最初のログインを済ませ、パスワードを変えてあること）。取り込み先に顧客が
  1 つでもあると取り込みません（カレンダー JP_BANK はあってよい。足りない休日だけ足します）

コマンドは開発 PC のリポジトリで（`requirements-dev.txt` を入れた venv。パスワードは実行のときに聞かれます）。
開発 PC がプロキシを通っているときだけ、`NO_PROXY` にサーバーのアドレスを入れておきます（サーバーへは直接つなぐ。
[README.md](README.md) の付録の 6.）。

- [ ] 取り込む前のバックアップ（サーバーで）: `docker compose exec backup sh /backup.sh once`
- [ ] テスト環境から書き出す（読むだけ）:
  `python -m scripts.export_seed --source <テスト環境の API の URL> --login <業務管理者> --out seed_data.json`
  - URL は、開発 PC の uvicorn なら `http://localhost:8000`、サーバーなら `http://<サーバー>/api`
  - [ ] 最後の行の件数（calendars・clients・businesses・dependencies・sops・sheets・templates）が、テスト環境の画面と合っている
  - [ ] 「人が変えたシートの日付」の一覧を確かめる（今の日付だけを持っていき、動かした・取り消した記録は持っていかない）
- [ ] 確かめだけ（何も作らない）:
  `python -m scripts.import_seed --target http://<サーバー>/api --login admin --seed seed_data.json --effective-date <使い始めの日> --dry-run`
  → `dry run: OK`。「今日より前の休日 N 件は足さない」は正常です（過去の日付は運用の記録で、予定は今日から先に作るため）
- [ ] 取り込む: 同じコマンドから `--dry-run` を外す → 最後に `done: 件数はファイルと同じ`
  - 途中で止まったら、作りかけのものが残っています。**上のバックアップに戻して**（[README.md](README.md)「6.3 データベースをバックアップから戻す」）
    から、原因を直してもう一度
- [ ] 取り込んだあとは、下の手順のうち確かめの項目だけを行います: 設定 → SOP で各業務の版が「予定」（使い始めの日から）、
  業務の設定（リリース・実行の種類）、シートの日付をいくつか見比べる、カレンダーの画面に予定が並んでいる

### C-1. 画面で 1 つずつ入れる

- [ ] 設定 → 顧客 →「顧客を登録」（コードは英数字 4 文字。あとで変えられません）
- [ ] 設定 → 業務 → その顧客を選んで「業務を登録」（業務コードは自動で付きます）。業務ごとに繰り返す
- [ ] 手順書のある業務は 設定 → SOP:「新しい版」→「ステップを追加」→「承認…」
  - **使い始めの日は最も早くて明日**です。それより前のオーダーはステップなし（SOP の版なし）でリリースされるので、
    パイロットの最初のオーダーの **前の日まで** に承認しておきます
- [ ] **年間計画シート**（顧客の年間計画の日付から予定を作る業務があるとき。テンプレートより先に入れます）:
  - 顧客の表（Excel など）から JSON ファイルへの変換は、システムの外で行います。ファイルの形は
    [操作マニュアル](../docs/OPERATION-MANUAL.md) の「年間計画シート」を見てください
  - [ ] 設定 → 年間計画シート → 顧客を選ぶ →「シートを取り込む」→ JSON ファイルを選ぶ
  - [ ] 取り込む前の表示で、顧客コード・シート名・期間・マーカーと日付の件数が、元の表と合っている
  - [ ] 「取り込む」→ 結果の「追加したマーカー」「追加した日付」がファイルの件数と同じ
  - [ ] 一覧でマーカーの行を開き、日付をいくつか元の表と見比べる（月初・月末・年末年始）
  - [ ] 毎月 27 日のように決まりで作れる基準日は、同じシートに「マーカーを追加」→「ルールで作る」で足す
  - ファイルが無いとき（日付が少ない顧客など）は、「新しいシート」で空のシートを作り、「マーカーを追加」→「日付を選んで作る」と
    「日付を編集（カレンダー）」で日付を入れても構いません
  - 次の年の分が届いたら、その年だけのファイルを同じシート名で「追加だけ」で取り込みます（期間は自動で広がり、今ある日付は消えません）。
    出し直された表に合わせて日付を消したいときだけ「ファイルに合わせる」を使います
    （**ファイルに日付が 1 件も無いマーカーは日付がすべて消える**ので、全マーカーの全期間の日付を入れたファイルで行います）
- [ ] 業務の行の「予定テンプレート・業務の設定」→ 業務の設定の「編集」:
  - リリース:「手動（リリース担当が承認）」か「自動（指定の時刻に）」（`worker` がリリース。既定は当日 03:00）
  - 顧客側の出来事（ファイルの受領など）の業務は「顧客側の出来事（ステップなし）」+「作業者が受領を記録する」
- [ ] 同じ画面の「新規作成」で予定テンプレートを作る: カレンダーは「銀行営業日」、時刻・所要時間・休日の扱い、
  締切（予定の終了 / 開始から / 固定の時刻）と、まもなくの表示を何分前から出すか（0 = 出さない）
  - シートの日付から作る業務は、種類を「年間計画シート」にして、シート・「参照するマーカー」・基準日のずれ
    （例: 3 営業日前）を選びます
- [ ] 業務どうしの順番があるときは 設定 → 業務の依存関係 →「依存関係を追加」
- [ ] カレンダーの画面で、その顧客の今月・来月に予定が並んでいる

## D. 職員

- [ ] 設定 → 職員 →「職員を登録」（ログイン ID・氏名・ロール）→「有効化」→「仮パスワード」
- [ ] 仮パスワードを本人に伝える（本人は最初のログインで自分のパスワードに変えます）
- [ ] ロールの組み合わせを確かめる:

  | ロール | すること |
  |---|---|
  | 作業者 | オーダーの開始、ステップの提出 |
  | 確認者 | ステップの承認・差し戻し（**提出した人とは別の人**） |
  | リリース担当 | 手動の業務のリリース、前倒しの開始・依存関係を待たない開始の承認、予定テンプレートの変更の下書き、SOP の草稿と承認の依頼、業務のリリース設定の変更 |
  | 業務管理者 | 設定の変更、テンプレートの下書きと SOP の草稿の承認・差し戻し、取消・矛盾の解決など判断が必要な操作 |
  | システム管理者 | 職員アカウントの管理（業務の操作は含まない） |

  - [ ] 作業者と確認者が別の人に割り当たっている（同じ人は自分の提出を承認できません）
  - [ ] 手動リリースの業務があるなら、リリース担当が少なくとも 1 人いる
  - [ ] リリース担当がテンプレートの変更や SOP の草稿を書くなら、承認する業務管理者が少なくとも 1 人いる（承認されるまで反映されない）
  - [ ] リリース担当は業務のリリース設定（方法・時刻・何日前）を直接変えられる（すぐに効く。変更は業務の設定の「履歴」に残る）。任せてよい人だけにリリース担当を付ける
- [ ] mfa のアダプター（アラートを mfa に渡すスクリプト）を動かすときは、その専用のアカウントを作る: 「職員を登録」→
  ロールは「システム連携（読み取り）」だけ（パスワードは設定しない）→「有効化」→「API キー」→ 用途「mfa のアダプター」で発行し、
  キーをアダプターの担当者に渡す。`curl -H "Authorization: Bearer <キー>" http://<サーバー>/api/staff/me` が 200 を返すことを確かめる
- [ ] 一部の顧客だけを扱う職員がいるときは、「編集」→「担当顧客」で顧客を選ぶ（空 = 全顧客。システム管理者には付けない）。
  その職員でログインして、カレンダー・日次ダッシュボードにその顧客だけが出て、設定のメニューに「職員」が無いことを確かめる

## I. 並行稼働（14 日間）

旧来の mfa と新しいシステムを **14 日間（暦日）並べて動かし**、新しいシステムに任せてよいかを確かめます。
この間、mfa は **いままでの（旧の）mfa.txt を読み続けます**。新しいシステムは、アダプターが **別のフォルダー** に書く新の mfa.txt と、
QA のメールボックスだけに届くアラームのメールを出します。どちらも本番の動きは変えません。

**進め方は「毎晩は自動で記録し、人が見比べるのは初めと終わり」です**（2026-11-17 の決定）。旧の mfa.txt は、顧客ごとの作業を
計算する Excel とは別の **リマインダーの Excel**（開始の時刻が決まった作業・リマインダーの名前・.vbs のスクリプト・音）から作られ、
**月に 1 回** 設定されます。旧が 1 か月動かないので、違いはほぼすべて **初日の前に月全体を 1 回見比べる** ことで見つかります（I-1）。
期間中は、夜のタスクが新旧の写しと照合の結果を黙って残すだけで、毎朝の確認は要りません（I-2）。承認に数えるのは、
終わりに 14 晩すべてを見比べ直すまとめです（I-3）。

- 毎晩の写しは要ります: 新のシステムの時刻表は「まだ始めていない作業」だけなので、その日が過ぎると、その晩に何を知らせたかを
  あとから作り直せません
- 初日の前に見比べるのは: 期間中に設定の誤り（テンプレートの分類・時刻）が見つかると、それまでの晩は誤った設定のまま
  写しに残り、直しても NG のままです（名前の違いだけは別名の表で後から直せます）。終わりに初めて見つかると、14 日をやり直すことになります

- 始めるのは、サーバー（Ubuntu）にアドレスが付き、A〜G が終わってから（2026-11-16 の決定。PC で動かすと、スリープや更新の再起動が
  「途切れ」になり、ワーカーの承認が通りません）
- **承認の条件（3 つすべて）**:
  1. 旧の mfa.txt の Msg の行すべてに、新の mfa.txt の同じ作業の行がある（開始の差 3 分以内）。14 日すべての晩で
  2. ワーカーに承認に数える問題が無い（エラー・5 分を超える途切れ・きれいに止まらなかった実行。予定した停止は理由を記録する）
  3. 運用の QA チームが、新しい画面での宛先の変更と記録の確認が旧来より良いか速いと、書面で確かめる
- 参考: アダプターと照合 [adapters/mfa/README.md](../adapters/mfa/README.md)、画面 [操作マニュアル](../docs/OPERATION-MANUAL.md) の
  3.16（出来事・通知）・3.17（届かなかったアラーム）・3.18（通知の設定）・3.19（ワーカーの状態）
- 期間中の設定の誤りは **画面で直します**（だれがいつ直したかが履歴に残るように）。事前確認のスクリプトは読むだけです

### I-1. 始める前（初日の前の日まで）

- [ ] **旧の Windows サーバーから新しいシステムに届く**: 旧の Windows サーバー（例: 10.x.x.50）の PowerShell で
  `Invoke-RestMethod http://<サーバー>/api/health/worker` → `state: ok`（届かなければ、ファイアウォールと nginx を確かめる）
- [ ] **メールの設定**: `.env` に次を書き、`docker compose up -d worker` → `docker compose logs worker` の
  `Notification channels: email: SMTP smtp.internal.corp:25 (STARTTLS if offered) from ops-system-noreply@corp.com` を確かめる

  ```sh
  SMTP_HOST=smtp.internal.corp
  SMTP_PORT=25
  SMTP_USER=                                   # 空 = ログインしない（社内のリレーは社内のアドレスだけを受ける）
  SMTP_PASSWORD=
  SMTP_FROM_ADDRESS=ops-system-noreply@corp.com
  SMTP_STARTTLS=                               # 空 = サーバーが対応していれば使う
  APP_BASE_URL=http://<サーバー>               # メールの本文に入れる画面へのリンク
  ```

- [ ] **宛先**: 設定 → 通知の設定 → タブ「宛先」→「宛先を作る」: 名前「QA チーム」、`ops-qa-team@corp.com`、顧客 = 全顧客
  - [ ] 「テスト送信」→ 1 分ほどで「届いた」。QA のメールボックスに実際に届いた
- [ ] **ルール**: タブ「ルール」で「遅れ」「まもなく」のルールを作る。宛先は **「QA チーム」だけ**、
  知らせない時間帯 **22:00〜07:00・終わってから知らせる**（23:00 の遅れは 07:00 に届く）
  - **技術的な止め具はありません。期間中は顧客や個人のアドレスを宛先に足さないでください**（事前確認で毎回確かめます）

## J. 切り替え（mfa が新しいファイルで鳴る）

I. の承認のあとで、mfa が読むファイルを、リマインダーの Excel が作るファイルから **アダプターが作るファイル** に替えます。
開始の知らせ（Msg）が新しいシステムから来るようになります。設計の理由は設計書の「Cut-over: mfa rings from the new file」です。

- **リマインダーの Excel は止めません。** 移行の期間（長い）のあいだ、いままでどおり保守し、毎月動かします。止めるのは移行の最後です
- そのため、アダプターは **Excel のファイルを元に** mfa のファイルを作ります: 新しいシステムが出す開始の知らせ（同じ作業・3 分以内）は
  新しいシステムの行に置き換え（その行の音は Excel の音のまま。緊急度と鳴らす機器が変わらない）、新しいシステムが出さない知らせは
  Excel の行のまま残し、**.vbs のスクリプト（Shell の行）と、知らせの無い音の行は、そのまま写します**（29 種類のスクリプトが止まらない）
- mfa は 1 つのファイルしか読まず、ファイルが替わっても自分では読み直しません。アダプターが書いたあとに `MFA.exe /R` で読み直させます
  （前後 2 分に行の無い分を選ぶので、読み直しで知らせやスクリプトを取りこぼさない）

> アダプターの 2 つの手順（M.1 Excel のファイルとの組み合わせ、M.2 `MFA.exe /R` での読み直し）は作りました（2026-11-17）。
> 設定は `mfa_adapter.ini` の `[cutover]`（[adapters/mfa/README.md](../adapters/mfa/README.md) の「切り替えのあと」）。
> **本物の mfa ではまだ動かしていません**。J-1 の試しの PC で確かめてから使います。

### J-1. 試しの PC で確かめる（切り替えの前に 1 回）

旧の Windows サーバーとは別の PC に、同じ版の mfa と音のファイル・スクリプトの置き場所（または試しのスクリプト）を用意し、
mfa にはアダプターの出力を読ませます。数分先に開始がある予定（不定期・「開始時刻に知らせる」オン）を 2〜3 件作っておきます。

- [ ] アダプターを手で動かし、出力に、新しいシステムの知らせ・Excel のファイルから写した Shell の行・音の行が入っている
- [ ] `MFA.exe /R` で読み直したあと、その時刻に **知らせの文（日本語）が正しく出て**、**決まった機器で、決まった音** が鳴る
- [ ] Shell の行（試しのスクリプト）が、その時刻に動く
- [ ] 読み直しにかかった時間を測った: ____ 秒。読み直しの最中・直前の分にある行が、鳴る / 鳴らない（どちらかを書く）
- [ ] 読み直しの前の時刻の行（過去の行）を、mfa が読み直しのあとにまとめて動かさない
- [ ] 結果を承認の記録（下）に書いた

### J-2. 切り替えの前の日まで

- [ ] 切り替えの日を決めた（なるべく月の変わり目。運用の担当が翌月のファイルを Excel から書き出す日に合わせる）
- [ ] **Excel から書き出した txt の置き場所を、mfa のファイルとは別の場所に替えた**（例: `D:\mfa\excel\mfa.txt`）。Excel は txt を
  自動では書き出さず、運用の担当が手で保存して通信サーバーに置いているので、**その担当者に、切り替えの日からは新しい置き場所へ
  置くように伝え**、手順書（担当者のメモ）も直した。いままでの mfa のファイルに直接置くと、アダプターの結果を上書きしてしまう
- [ ] アダプターの設定（`mfa_adapter.ini`。切り替えの日まで `enabled = false` のまま書いておく）:
  - `[cutover] excel_file` = その別の置き場所の txt、`live_file` = **mfa が読む本物のファイル**、`mfa_exe` = 通信サーバーの `MFA.exe`
    の場所（`reload_args = /R` のまま）
  - `[parity] legacy_file` も `excel_file` と同じにする（照合は、組み合わせる **前** の新しいシステムの知らせと見比べるので、

- [ ] いま mfa が読んでいるファイルを、日付つきの名前で写して残した（戻すときに使う）

### J-5. 移行の期間中

- 新しい作業の知らせは、**Excel と新しいシステムの両方** に入れます（Excel は止めないため）。新しいシステムに入れ忘れても、Excel の知らせが

- Excel を止めること（スクリプトと音を新しいシステムとアダプターの設定に移す）は、移行の最後の段階で、別の手順として決めます
