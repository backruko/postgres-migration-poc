# 本番の使い始め（チェックリスト）

サーバーを立てたあと、実際に使い始めるまでに 1 回だけ行う作業です。上から順に進め、終わったら `[x]` にします。
最初は **1 つの顧客だけ**（パイロット）で始め、数日使って問題がなければ残りの顧客を足します（H）。
サーバーの立て方・更新・ログ・バックアップの基本は [README.md](README.md) を見てください。

- コマンドはすべて `deploy` フォルダーで実行します（`docker compose …`）。
- `-U ops -d ops` は `.env` の `POSTGRES_USER` / `POSTGRES_DB` です。違う値にしたときは読み替えてください。
- 画面の操作には **業務管理者**（設定の変更）や **システム管理者**（職員の管理）のロールが要ります。

## A. 事前の確認（データを入れる前）

- [ ] `docker compose ps` で `db` / `app` / `worker` / `web` / `backup` が動いていて、`app` が `healthy`
- [ ] ブラウザで `http://<サーバー>/` を開くとログイン画面が出る
- [ ] `docker compose logs worker` に `Worker started (automatic release every minute, …)` が出ている
- [ ] `docker compose logs backup` に `backup: daily at 01:00, keeping 14 days in /backups` が出ている
- [ ] **復元の練習**（本番のデータには触らず、別のデータベースへ戻して比べる）:

  ```sh
  docker compose exec backup sh /backup.sh once        # 今すぐバックアップ（ファイル名がログに出る）
  ls backups/                                          # .env の BACKUP_DIR を変えたときはそのフォルダー
  docker compose exec db createdb -U ops ops_restore_check
  docker compose exec -T db pg_restore --no-owner -U ops -d ops_restore_check < backups/ops_YYYYMMDD_HHMMSS.dump
  docker compose exec -T db psql -X -A -t -U ops -d ops < restore-check.sql
  docker compose exec -T db psql -X -A -t -U ops -d ops_restore_check < restore-check.sql
  docker compose exec db dropdb -U ops ops_restore_check
  ```

  - [ ] `pg_restore` がエラーを出さずに終わる
  - [ ] 2 つの `psql` の結果（alembic の版と各テーブルの件数）が同じ
  - [ ] 最後に `ops_restore_check` を消した

## B. 最初の設定

- [ ] 最初の管理者を作る（パスワードを 2 回たずねます）:
  `docker compose exec app python scripts/create_staff.py admin "管理者の氏名" --roles system_admin admin`
- [ ] 営業日カレンダーを作る（土日休み。2 回動かしても変わりません）:
  `docker compose exec app python scripts/setup_calendar.py`
  → `Created business calendar id=1 code=JP_BANK name=銀行営業日 weekend_days=[6, 7]`
- [ ] `admin` でログインできる。右上の名前のメニューに「パスワードを変更」「ログアウト」がある
- [ ] 設定 → 休日カレンダー →「銀行営業日」:
  - [ ] 今年と来年それぞれ「日本の祝日を取り込む」（今日より前の日付と登録済みの日付は取り込まれません）
  - [ ] 銀行の休業日を「休日を追加」で足す: 12/31、1/2、1/3（土日に当たる年も登録してかまいません）

## C. パイロットの顧客を 1 つ入れる

- [ ] 設定 → 顧客 →「顧客を登録」（コードは英数字 4 文字。あとで変えられません）
- [ ] 設定 → 業務 → その顧客を選んで「業務を登録」（業務コードは自動で付きます）。業務ごとに繰り返す
- [ ] 手順書のある業務は 設定 → SOP:「新しい版」→「ステップを追加」→「承認…」
  - **使い始めの日は最も早くて明日**です。それより前のオーダーはステップなし（SOP の版なし）でリリースされるので、
    パイロットの最初のオーダーの **前の日まで** に承認しておきます
- [ ] 業務の行の「予定テンプレート・業務の設定」→ 業務の設定の「編集」:
  - リリース:「手動（リリース担当が承認）」か「自動（指定の時刻に）」（`worker` がリリース。既定は当日 03:00）
  - 顧客側の出来事（ファイルの受領など）の業務は「顧客側の出来事（ステップなし）」+「作業者が受領を記録する」
- [ ] 同じ画面の「新規作成」で予定テンプレートを作る: カレンダーは「銀行営業日」、時刻・所要時間・休日の扱い、
  締切（予定の終了 / 開始から / 固定の時刻）と、まもなくの表示を何分前から出すか（0 = 出さない）
- [ ] 業務どうしの順番があるときは 設定 → 業務の依存関係 →「依存関係を追加」
- [ ] カレンダーの画面で、その顧客の今月・来月に予定が並んでいる

## D. 職員

- [ ] 設定 → 職員 →「職員を登録」（ログイン ID・氏名・ロール）→「有効化」→「仮パスワード」
- [ ] 仮パスワードを本人に伝える（本人は最初のログインで自分のパスワードに変えます）
- [ ] ロールの組み合わせを確かめる:

  | ロール | すること |
  |---|---|
  | 作業者 | オーダーの開始、ステップの提出 |
  | 確認者 | ステップの承認・差し戻し（**提出した人とは別の人**） |
  | リリース担当 | 手動の業務のリリース、前倒しの開始・依存関係を待たない開始の承認 |
  | 業務管理者 | 設定の変更、取消・矛盾の解決など判断が必要な操作 |
  | システム管理者 | 職員アカウントの管理（業務の操作は含まない） |

  - [ ] 作業者と確認者が別の人に割り当たっている（同じ人は自分の提出を承認できません）
  - [ ] 手動リリースの業務があるなら、リリース担当が少なくとも 1 人いる

## E. オーダー

- [ ] 日次ダッシュボードで、パイロットの顧客の予定の行に「未リリース」が付いている
  （テンプレートを作ると、その時点で先の予定のオーダーが自動でできます）
- [ ] 念のため `docker compose exec app python scripts/create_orders.py` → `Created 0 orders`（足りないものだけ作ります。何回動かしても同じ）

## F. ブラウザでの確認（パイロットの職員で）

- [ ] 間違ったパスワード → 「ログインIDまたはパスワードが違います。」の表示。5 回でロックされ、15 分後の時刻が出る
- [ ] 仮パスワードでログイン → パスワードの変更の画面が出て、変えるまでほかの画面に進めない
- [ ] ログアウト → ログイン画面に戻る。戻るボタンで画面に入れない
- [ ] 設定 → 顧客 / 業務 / SOP の画面が開き、作業者のアカウントでは変更のボタンが出ない
- [ ] 1 件のオーダーを最後まで: リリース → 開始 → ステップの提出 → 別の人が承認 → 全ステップ承認で「完了」
- [ ] 締切を過ぎた未完了のオーダーに「遅れ」、締切の前に「まもなく」が付く（締切・遅れのタブにも出る）

## G. 最初の数日

- [ ] 翌朝: 自動リリースの業務があれば `docker compose logs worker` に `Released … pending automatic orders` が出ている
- [ ] 翌朝: バックアップのフォルダーに 01:00 のファイル `ops_YYYYMMDD_0100xx.dump` がある
- [ ] NAS への同期を OS 側で設定した（バックアップのフォルダーを同期。`*.partial` は書き込み中なので外す）
- [ ] 2 日目以降: `docker compose logs worker` に毎日 00:05 過ぎの `Plan extension: …` が出ている

## H. 残りの顧客

- [ ] パイロットで問題がなければ、顧客ごとに C → D（新しい職員がいれば）→ E を繰り返す
